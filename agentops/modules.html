พื้นฐาน AI Agent + CI/CD ที่ต้องรู้

9 บทเรียนพร้อมตัวอย่าง แปลประโยคอังกฤษ และคำถามเช็กความเข้าใจ

ขอบเขตหลักฐาน บทเรียนอธิบายแนวคิดด้วยตัวอย่างสมมติ ส่วนผลทดลองเดิมในหน้าแก้ปัญหาและบทพูดอิงคำบอกเล่าจากภาพ ไม่ใช่สถานะ AWS ล่าสุด

เริ่มเรียนโดยไม่ต้องมีพื้นฐาน

นี่คือบทเรียนเรียงตามความเข้าใจ ไม่ใช่หมายเลข Module ของ AWS อ่านครั้งละ 1–2 หัวข้อแล้วลองตอบท้ายหัวข้อ เวลาน้อยให้เริ่ม 1, 2 และ 4 เพื่อเห็นภาพ agent กับ CI/CD

1 · โปรแกรม, server และ API

โปรแกรมคือชุดคำสั่งที่รับข้อมูล ประมวลผล และให้ผลลัพธ์ เช่นโปรแกรมรับ order_id แล้วหายอดคำสั่งซื้อ ส่วน server คือโปรแกรมหรือเครื่องที่รอรับคำขอจากอีกฝั่ง client คือฝ่ายส่งคำขอ Mac ของเราอาจเป็น client แต่โปรแกรมที่ตอบกลับรันบน cloud

API (Application Programming Interface) คือข้อตกลงให้โปรแกรมคุยกัน เช่นต้องส่ง order_id เป็นข้อความ แล้วจะได้สถานะกับยอดกลับมา Request คือข้อมูลที่ส่งไป Response คือข้อมูลที่ตอบกลับ Endpoint คือจุดรับคำขอ ในบทเรียนบางช่วงหมายถึง URL และใน AgentCore หมายถึงปลายทาง Runtime ที่เลือกเวอร์ชันด้วย ต้องดูบริบท

JSON คือรูปแบบข้อมูล key/value เช่น {"order_id":"DEMO-01","total_cents":8000} เป็นข้อมูลจำลอง ตัวเลข 8000 ต่างจากข้อความ "8000" Schema คือข้อกำหนดว่าข้อมูลต้องมี field อะไรและเป็นชนิดใด ถ้า API คาดตัวเลขแต่ส่งข้อความ อาจถูกปฏิเสธก่อนทำงาน

HTTP เป็นวิธีส่งคำขอผ่านเครือข่ายที่พบบ่อย GET มักใช้ขอข้อมูล POST มักใช้ส่งข้อมูลเพื่อประมวลผล แต่ต้องอ่าน API จริง ไม่ตัดสินผลกระทบจากชื่อ method อย่างเดียว Status code เช่น 2xx บอกระดับ HTTP สำเร็จ ส่วน 4xx/5xx บอกกลุ่มปัญหา ยังต้องอ่าน response body เพื่อดูผลธุรกิจ

ตัวอย่างเชื่อมภาพ

ผู้ใช้ขอดูคำสั่งซื้อ → client ส่ง order_id → API ตรวจ input → โปรแกรมค้นข้อมูล → ส่ง JSON กลับ ข้อมูลกลับมาแล้วไม่ได้แปลว่ามีการคืนเงิน

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

Send a request to the endpoint.

ส่งคำขอไปยังปลายทาง

จับกริยา Send = ส่ง, กรรม a request = ข้อมูลคำขอ, ปลายทาง endpoint ถามต่อว่า payload ต้องมี field อะไร

ลองตอบ: ได้ HTTP success แล้วแปลว่าคืนเงินสำเร็จเสมอไหม?

ไม่เสมอ ต้องอ่านผลธุรกิจจาก response และดูว่า operation ที่เรียกคือดูข้อมูลหรือออกเงินคืน

2 · LLM, prompt, agent และ tool

LLM (Large Language Model) คือโมเดลภาษาที่ประมวลผลข้อความและสร้างคำตอบ Prompt คือคำสั่งหรือข้อมูลที่ส่งให้โมเดล Context คือข้อมูลที่มีให้พิจารณาในรอบนั้น เช่นบทสนทนาและผลเครื่องมือ โมเดลไม่ได้รู้สถานะคำสั่งซื้อปัจจุบันเพียงเพราะถามเป็นภาษาไทยหรืออังกฤษ

Agent คือโปรแกรมที่ใช้โมเดลร่วมกับตรรกะและเครื่องมือเพื่อทำงาน ตัวโปรแกรมกำหนดว่าเครื่องมือไหนใช้ได้ วิธีรับผล และเงื่อนไขหยุด บางงานต้องเรียก tool หลายรอบ บางงานตอบได้ทันที Agent จึงไม่ใช่แค่ prompt ยาวหนึ่งชุด

Tool คือความสามารถที่โปรแกรมเปิดให้ agent เรียก เช่น lookup_order, get_refund_policy และ issue_refund ชื่อสองตัวแรกในตัวอย่างนี้ใช้เพื่ออธิบาย ไม่ใช่การยืนยันชื่อจริงในแล็บ Tool มีชื่อ คำอธิบาย และ input schema ที่ช่วยให้โมเดลเลือกและสร้าง arguments ได้

Tool call คือคำขอใช้เครื่องมือพร้อม arguments ส่วน tool result คือผลจากการรันจริง โดยทั่วไปโมเดลเสนอการเรียก จากนั้นโปรแกรมตรวจและดำเนินการตามสิทธิ์ แล้วนำผลกลับให้โมเดล ไม่ใช่ให้ข้อความของโมเดลเปลี่ยนฐานข้อมูลเอง

วงรอบตัวอย่าง: รับคำถาม → อ่าน context → เลือก tool → ตรวจและเรียก tool → ได้ผล → ตัดสินใจว่าต้องเรียกเพิ่มหรือพอตอบแล้ว ควรกำหนดขีดจำกัดเวลา/จำนวนรอบและจัดการ error เพราะ agent อาจเลือกเครื่องมือผิดหรือวนซ้ำได้

ตัวอย่างเชื่อมภาพ

คำถาม “ขอคืนเงินรายการนี้” ต้องรู้ข้อมูลคำสั่งซื้อและเงื่อนไขก่อน เมื่อ tool ปฏิเสธ agent ควรอธิบายว่าทำไม่ได้ ไม่แต่งว่า Refund processed

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

The agent invokes a tool and returns a response.

agent เรียกเครื่องมือแล้วส่งคำตอบกลับ

invoke = เรียกใช้งาน, returns = ส่งกลับ ต้องแยกว่า response ที่พูดถึงเป็นผล tool หรือคำตอบสุดท้ายของ agent

ลองตอบ: Prompt บอกว่าอย่าคืนเงินเกินวงเงิน เพียงพอแทนระบบสิทธิ์ไหม?

ไม่เพียงพอ Prompt ช่วยชี้พฤติกรรม แต่การอนุญาตให้เกิดผลจริงควรตรวจในชั้นโปรแกรม/เครื่องมือ/นโยบายด้วย

3 · Git, version และสิ่งที่ต้องเก็บร่วมกัน

Source code คือไฟล์โปรแกรม Repository หรือ repo คือที่เก็บไฟล์และประวัติ Git เป็นเครื่องมือบันทึกการเปลี่ยนแปลง Commit คือจุดบันทึกที่อ้างอิงกลับได้ Branch คือเส้นทางพัฒนาชุดหนึ่ง Pull request หรือ PR ใช้เสนอให้ทีมตรวจและรวมการเปลี่ยนแปลงตาม workflow

การบันทึกไฟล์ใน editor ยังไม่เท่ากับ commit และ commit ในเครื่องยังไม่เท่ากับ push ขึ้น remote ส่วน merge คือรวมการเปลี่ยนแปลงเข้าด้วยกัน การ push ไม่ได้แปลว่า deploy เสมอ ต้องดูว่ามี pipeline เชื่อมกับเหตุการณ์นั้นหรือไม่

Version คือชุดการเปลี่ยนแปลงที่แยกจากชุดอื่นได้ แต่ละระบบอาจมีเลขอ้างอิงต่างกัน เช่น commit ID, image tag และ Runtime version อย่าคิดว่าทั้งสามใช้เลขเดียวกันโดยอัตโนมัติ ต้องมีวิธีเชื่อมว่า Runtime นี้มาจาก source ชุดใด

สำหรับ agent สิ่งที่มีผลต่อพฤติกรรมไม่ได้มีแค่โค้ด แต่รวม prompt, model configuration, tool schema, dependency และ policy ที่เกี่ยวข้อง การเปรียบเทียบผลทดสอบควรรู้ว่าชุดไหนเปลี่ยน ไม่เปลี่ยนหลายอย่างแล้วสรุปว่าดีขึ้นเพราะ prompt อย่างเดียว

Artifact คือผลที่เตรียมไว้ส่งต่อ เช่น package หรือ container image Container image เปรียบเป็นชุดไฟล์และสภาพแวดล้อมที่เตรียมสำหรับรัน ส่วน container คือ instance ที่กำลังรัน ไม่ต้องเรียน Docker ทุกคำสั่งก่อน แต่ต้องรู้ว่า build กับ run คนละขั้น

ตัวอย่างเชื่อมภาพ

แก้ prompt ใน branch → ดู diff → ทดสอบ → commit → เปิด PR ให้ทีม review → รวมตาม workflow เมื่อ pipeline ถูก trigger จึงเริ่มขั้นตรวจของ pipeline

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

Commit your changes and push the branch.

บันทึกการเปลี่ยนแปลงใน Git แล้วส่ง branch ไป remote

changes หมายถึงไฟล์ที่แก้ ไม่ใช่ผล AWS ที่สำเร็จ และประโยคนี้ยังไม่ได้บอกให้ deploy

ลองตอบ: ถ้า staging กับ prod ตอบต่างกัน ต้องเริ่มสงสัยว่ารุ่นโมเดลต่างกันเท่านั้นหรือไม่?

ไม่ใช่ ตรวจ source/version, prompt, config, tool/policy และข้อมูลที่ใช้ด้วย ไม่ฟันธงที่โมเดลก่อน

4 · CI/CD: เส้นทางส่งเวอร์ชันใหม่

CI (Continuous Integration) คือแนวปฏิบัติรวมการเปลี่ยนแปลงและตรวจอย่างสม่ำเสมอ เช่นตรวจ syntax รัน tests และตรวจ dependency เพื่อพบปัญหาเร็ว ส่วน CD อาจหมายถึง Continuous Delivery คือเตรียมพร้อมส่งมอบโดยมีการอนุมัติ หรือ Continuous Deployment คือปล่อยโดยอัตโนมัติเมื่อผ่านเงื่อนไข ต้องฟังว่าทีมใช้ความหมายใด

Pipeline คือชุดขั้นตอนที่ถูกเรียกตาม trigger เช่นการ push หรือเริ่มโดยผู้มีสิทธิ์ Stage คือกลุ่มขั้นตอนหนึ่งช่วง Action/job คือหน่วยงานที่ทำภายใน Execution/run คือการทำงานของ pipeline หนึ่งรอบ ภาพสถานะต่างรอบไม่ควรนำมารวมเป็นรอบเดียว

เส้นทางตัวอย่างทั่วไป: Source → Build → Test/Evaluation → Deploy to staging → Approval → Promote to production แต่ละทีมจัดลำดับและชื่อ stage ต่างกัน ตัวอย่างนี้สอนแนวคิด ไม่อ้างว่าเป็นโครงแล็บจริงทั้งหมด

Build คือเตรียมสิ่งที่จะรัน Test/Evaluation คือตรวจคุณภาพ Deploy คือเอา artifact/config ไปวางให้ทำงาน ส่วน Promote คือเลื่อนเวอร์ชันที่เลือกไปปลายทางถัดไป บางระบบเลื่อนโดยเปลี่ยน endpoint ให้ชี้ version จึงไม่จำเป็นต้องเขียนโค้ดใหม่ทุกครั้ง

dev เป็นพื้นที่พัฒนา staging เป็นพื้นที่ตรวจความพร้อมก่อนใช้งานจริง prod เป็น production ตามที่ทีมกำหนด ชื่อเหล่านี้ไม่ได้รับรองว่าทรัพยากรแยกบัญชีหรือ config เหมือนกัน ต้องดูการจัดระบบ

Approval คือด่านรอผู้มีสิทธิ์พิจารณา Pending approval หมายถึงยังรอ ไม่ใช่ผ่านแล้ว Rollback คือกลับไปชุดที่เคยใช้ได้ แต่ไม่ได้ย้อนข้อมูลหรือธุรกรรมที่เกิดไปแล้วทั้งหมด เช่นเปลี่ยน version กลับไม่ได้ยกเลิกเงินคืนอัตโนมัติ

ตัวอย่างเชื่อมภาพ

นักพัฒนาแก้ agent → pipeline ตรวจ → staging ทดสอบ → ผู้รับผิดชอบพิจารณา prod นี่เป็นเส้นทางตอนเปลี่ยนเวอร์ชัน ไม่ได้เกิดใหม่ทุกครั้งที่ลูกค้าส่งข้อความ

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

The pipeline is waiting for manual approval.

pipeline กำลังรอคนอนุมัติ

waiting for = รอ, manual = คนดำเนินการ ยังไม่ใช่ approved หรือ promoted

ลองตอบ: ลูกค้าคุยกับ agent หนึ่งครั้ง ต้อง build และ deploy ใหม่หรือไม่?

โดยทั่วไปไม่ ต้องแยกเส้นทางคำขอผู้ใช้กับเส้นทางพัฒนา/ปล่อยเวอร์ชัน Agent ที่ deploy แล้วรับคำขอได้หลายครั้ง

5 · Test, evaluation และเกณฑ์ผ่าน

Test คือการตรวจพฤติกรรมที่คาดได้ เช่นจำนวน cents ต้องเป็นจำนวนเต็มหรือ order ID หายแล้วต้องคืน error Unit test ตรวจส่วนเล็ก Integration test ตรวจส่วนที่เชื่อมกัน End-to-end test ตรวจเส้นทางตั้งแต่ต้นถึงผลปลายทาง ขอบเขตต่างกันจึงแทนกันทั้งหมดไม่ได้

Evaluation คือประเมินคุณภาพตามโจทย์ เช่นคำตอบตรงคำถาม เลือก tool ถูก และอ้างผล tool ถูกหรือไม่ Dataset คือชุดกรณีทดสอบ Expected result คือผลที่ต้องการ Evaluator คือวิธีให้ผล Rubric คือรายละเอียดเกณฑ์ และ threshold คือเกณฑ์ตัดสินผ่าน

บางเงื่อนไขตรวจด้วยโค้ดตรง ๆ ได้ เช่นต้องไม่เรียก issue_refund เมื่อถูกปฏิเสธ บางเงื่อนไขให้คนหรือโมเดลช่วยตัดสิน เช่นความชัดของคำอธิบาย การใช้โมเดลประเมินยังมีความแปรปรวนและข้อจำกัด จึงควรตรวจตัวอย่างและไม่เชื่อคะแนนเดียวโดยไม่ดูหลักฐาน

Regression คือสิ่งที่เคยทำได้แล้วกลับแย่ลงหลังเปลี่ยน เช่นแก้ให้ตอบสุภาพขึ้นแต่เรียก tool ผิด Evaluation gate ใช้หยุดการเลื่อนเวอร์ชันเมื่อไม่ผ่านเกณฑ์ที่ตั้งไว้ แต่ผ่าน gate ไม่ได้พิสูจน์เคสที่ไม่มีในชุดทดสอบ

Offline/on-demand evaluation ใช้ชุดข้อมูลหรือ traces ที่เลือกมาประเมินเป็นรอบ ส่วน online evaluation ประเมินจากการใช้งานที่เข้ามาตาม configuration อาจเลือกบางส่วนด้วย sampling ทั้งสองช่วยกันคนละเวลา การกรอกแบบฟอร์มตั้งค่าไม่เท่ากับมีผลประเมินแล้ว

ตัวอย่างเชื่อมภาพ

ชุดจำลองควรมีทั้งคืนเงินได้ เกินวงเงิน เกินวัน ข้อมูลหาย และ tool error พร้อมตรวจคำตอบและการเรียก tool ไม่ใช่ตรวจว่า agent มีข้อความตอบกลับอย่างเดียว

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

Run the evaluation and check whether it meets the threshold.

รันการประเมิน แล้วตรวจว่าผลถึงเกณฑ์หรือไม่

whether = ว่า...หรือไม่, meets = ถึง/ผ่าน, threshold = เส้นเกณฑ์ ต้องถามว่าเกณฑ์วัดอะไรและกรณีใด

ลองตอบ: Evaluation API แจ้ง input invalid ถือว่า agent ได้คะแนนศูนย์ไหม?

ไม่ใช่ เป็นรอบที่ input ไม่ผ่าน validation จึงต้องแก้ข้อมูลก่อนอ่านผลประเมิน ไม่ตีความ error เป็นคะแนน

บทเรียนพื้นฐาน · ตัวอย่างเพื่ออธิบาย

6 · AWS: แต่ละส่วนอยู่ชั้นไหน

AWS เป็นแพลตฟอร์มบริการ cloud Console คือหน้าเว็บจัดการ CLI คือสั่งผ่านข้อความ SDK คือ library ที่โค้ดเรียกบริการ ทั้งสามอาจใช้ API เดียวกัน แต่แต่ละสภาพแวดล้อมต้องมี credentials และสิทธิ์ที่ถูกต้อง

Account คือบัญชีทรัพยากร Region คือภูมิภาค IAM จัดการตัวตนและสิทธิ์ Role คือบทบาทที่รับสิทธิ์ตามเงื่อนไข Authentication ถามว่าเป็นใคร ส่วน authorization ถามว่าทำอะไรได้ ล็อกอินสำเร็จไม่ได้แปลว่ามีสิทธิ์ทุก action

Runtime รันโปรแกรม agent ส่วน endpoint เป็นปลายทางเรียก version/configuration ที่ต้องการ ใน AgentCore ต้องตรวจว่า endpoint dev หรือ prod ชี้ Runtime version ใด ไม่เดาว่ามันเปลี่ยนตามรุ่นล่าสุดเสมอ

Gateway เชื่อม agent ไปเครื่องมือ Target คือปลายทางที่ผูกไว้ Lambda เป็นบริการรันฟังก์ชันโดยเราไม่ต้องจัดการ server เองทุกส่วน ฟังก์ชันยังต้องมีโค้ด สิทธิ์ และจัดการ error เช่นงานคืนเงิน

CloudWatch ใช้ติดตาม logs/metrics ส่วน CloudFormation จัดชุดทรัพยากรด้วยแม่แบบเรียกว่า stack การสร้าง stack สำเร็จบอกเรื่องโครงสร้าง ไม่ใช่ทดสอบเงื่อนไขธุรกิจครบแล้ว

ตัวอย่างเชื่อมภาพ

เครื่องที่พิมพ์คำสั่ง → บัญชี/region ที่เลือก → Runtime รัน agent → เครื่องมือผ่าน Gateway → ฟังก์ชันทำงานหากได้รับอนุญาต นี่เป็นภาพองค์ประกอบทั่วไป ไม่กำหนดลำดับภายใน policy/interceptor

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

Verify that the endpoint points to the intended version.

ตรวจว่า endpoint ชี้เวอร์ชันที่ตั้งใจ

verify = ตรวจยืนยัน; points to = ชี้ไปยัง; intended = ที่ต้องการ ไม่ใช่แค่เห็น READY

ลองตอบ: Resource ไม่ปรากฏแปลว่าถูกลบแล้วไหม?

ยังสรุปไม่ได้ ตรวจบัญชี region สิทธิ์ และ ID ก่อน

บทเรียนพื้นฐาน · ตัวอย่างเพื่ออธิบาย

7 · Policy ควบคุมอะไร

Prompt กำกับพฤติกรรมโมเดล ส่วน policy เป็นกฎที่ชั้นควบคุมใช้ตัดสินสิทธิ์ ก่อนการกระทำมีผลจริงควรตรวจในระบบ ไม่ฝากไว้กับข้อความที่โมเดลบอกว่าจะทำ

Principal คือผู้กระทำ Action คือสิ่งที่จะทำ Resource คือสิ่งที่กระทำต่อ Context คือข้อมูลประกอบ Cedar เป็นภาษาสำหรับเขียนกฎสิทธิ์แบบนี้ ต้องตรวจทั้ง scope และเงื่อนไข ไม่ดูแค่จำนวนเงิน

Interceptor แทรกในเส้นทางเพื่ออ่าน ตรวจ หรือปรับข้อมูล ส่วน policy ตัดสินจากข้อมูลที่ได้รับ การ log ว่าเติมยอดเสร็จไม่พิสูจน์ว่าตัวตัดสินเห็นยอดด้วย path/type เดียวกัน ต้องตรวจ input ที่ใช้จริง

สมมติกฎห้าม order_total_cents > 10000: 25000 cents คือ $250 เข้าเงื่อนไข แต่เท่ากับ 10000 ไม่เข้าเงื่อนไขมากกว่า อย่างไรก็ตามต้องมีสิทธิ์อนุญาตและผ่านกฎอื่นด้วย Field นี้คือยอด order ตามโจทย์ ไม่ควรเปลี่ยนความหมายเป็นเงินคืนบางส่วนเอง

ACTIVE/ENFORCE บอกสถานะหรือโหมด configuration ส่วน ALLOW/DENY บอก decision ของคำขอหนึ่งรอบ แยกสองระดับนี้แล้วจะไม่พูดว่า setup เสร็จจึงทดสอบทุกกรณีผ่าน

ตัวอย่างเชื่อมภาพ

ตรวจแยก: กฎที่ตั้ง → context คำขอ → decision → tool result คำตอบ agent อย่างเดียวแทนทุกชั้นไม่ได้

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

The request is denied because it exceeds the limit.

คำขอถูกปฏิเสธเพราะเกินขีดจำกัด

denied = ปฏิเสธ; exceeds = มากกว่า ต้องดูว่านี่เป็น decision จริงหรือข้อความที่ agent สรุป

ลองตอบ: เติมข้อมูลใน interceptor สำเร็จเท่ากับ policy สำเร็จไหม?

ไม่ ต้องตรวจข้อมูลที่ policy เห็น ขอบเขตกฎ ผลตัดสิน และผลปลายทาง

8 · Log, metric, trace และ debug

Log คือบันทึกเหตุการณ์ Metric คือค่าตัวเลขตามเวลา เช่นจำนวน error Trace คือร่องรอยงานที่เชื่อมหลายช่วง และ span คือช่วงงานย่อยใน trace เช่นการเรียก tool ครั้งหนึ่ง แต่ละชนิดตอบคำถามต่างกัน

Session คือกลุ่มการสนทนาที่อาจมีหลายคำขอและหลาย trace ไม่ใช้ session ID, trace ID และ span ID แทนกัน ดูเวลา endpoint/version และ identifiers ที่เกี่ยวข้องเพื่อจับคู่รอบเดียวกัน

Latency คือเวลาที่ใช้ตอบ Throughput คือปริมาณงานต่อเวลา Error rate คือสัดส่วนงานผิดพลาด ค่าเฉลี่ยอย่างเดียวอาจซ่อนเคสช้าหรือผิดมาก ต้องดูกรณีตัวอย่างประกอบ

Debug เริ่มจาก expected ว่าควรเกิดอะไร เทียบ observed ที่เกิดจริง แล้วลดขอบเขตไปชั้นที่ต่าง เช่นไม่ได้เรียก tool เรียกแล้ว error หรือ tool สำเร็จแต่ตอบผิด เปลี่ยนทีละจุดที่มีหลักฐานจะรู้ว่าอะไรช่วยแก้ได้

Retry คือการลองซ้ำ Idempotency คือออกแบบให้คำขอเดิมซ้ำไม่สร้างผลธุรกิจซ้ำโดยไม่ตั้งใจ Timeout บอกว่าไม่ได้รับคำตอบทันเวลา ไม่ได้พิสูจน์ว่าปลายทางไม่ทำงาน จึงไม่กดคืนเงินซ้ำโดยไม่ตรวจผลเดิม

ตัวอย่างเชื่อมภาพ

คำตอบผิด → หา trace รอบนั้น → หา span ของ tool → อ่าน input/output/error → เทียบคำตอบสุดท้าย ถ้าไม่มี span ต้องตรวจ telemetry ไม่เดาว่า tool ไม่ถูกเรียก

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

Inspect the trace to identify the failing tool call.

ตรวจ trace เพื่อหาการเรียกเครื่องมือที่ล้มเหลว

inspect = เปิดดู; identify = ระบุ; failing = ที่ผิด เริ่มด้วยคำถามว่าพังจุดใด

ลองตอบ: Timeout แล้วสั่งคืนเงินซ้ำได้ทันทีไหม?

ควรตรวจผลเดิมและกลไกป้องกันคำขอซ้ำก่อน เพราะรอบก่อนอาจทำงานแล้วแต่คำตอบมาไม่ถึง

9 · อ่านอังกฤษให้จับจุดได้

หา 4 ส่วนของประโยค: กริยาให้ทำอะไร → ทำกับสิ่งใด → ที่ไหน/รุ่นใด → คาดผลอะไร Verify the deployment status in the console คือดูสถานะใน Console ไม่ใช่ deploy อีกรอบ

Run the script คือคำสั่งให้รัน ส่วน You should see… คือผลที่ควรปรากฏ หากไม่ตรงหยุดตรวจตรงนั้นก่อน Prerequisite คือสิ่งที่ต้องพร้อม Optional คือทางเลือกที่ไม่บังคับในเส้นทางนั้น

Replace the placeholder คือแทนค่าตัวอย่างด้วยค่าที่ถูก เช่นโปรไฟล์ตามทีม ไม่คัดคำว่า YOUR_PROFILE ตามตัวอักษร Environment variable ต้องมีค่าใน shell ที่ใช้อยู่ หากไม่รู้ว่าค่ามาจากไหนให้ย้อนขั้นก่อน ไม่เดาเอง

Pending = รอ, in progress = กำลังทำ, succeeded = ขั้นนั้นสำเร็จ, failed = ล้มเหลว, skipped = ข้าม, enabled = เปิดใช้งาน อ่านพร้อมชื่อ stage/resource ไม่ขยายเป็นทั้งระบบสำเร็จ

ประโยคถาม: Which environment should I run this in? = รันที่ไหน; What output should I expect? = ควรได้ผลอะไร; Does this command change any resources? = เปลี่ยนทรัพยากรไหม; Could you explain how this step connects to the previous one? = ขั้นนี้เชื่อมกับขั้นก่อนอย่างไร

I expected X, but I got Y. I ran it in staging. = ผมคาดว่า X แต่ได้ Y และรันใน staging เพิ่มสิ่งที่ลองแล้วจะช่วยให้ผู้สอนวิเคราะห์ได้เร็ว

เจอภาษาอังกฤษแบบนี้ ให้อ่านว่า…

Before proceeding, ensure that the evaluation has completed successfully.

ก่อนทำต่อ ตรวจให้แน่ใจว่าการประเมินเสร็จสำเร็จแล้ว

Before proceeding = ก่อนขั้นถัดไป; ensure = ตรวจให้แน่ใจ; completed successfully = เสร็จสำเร็จ ไม่ใช่เพิ่งเริ่ม

ลองตอบ: You should see a success message คือให้พิมพ์ success ไหม?

ไม่ใช่ เป็นผลที่ควรเห็น ให้เทียบกับ output จริง
