22 คำ

AgentOps

การดูแลวงจรชีวิตของ AI agent

คือการทำให้ agent พัฒนา ทดสอบ ปล่อยใช้งาน และตรวจย้อนหลังได้อย่างเป็นระบบ คำตอบที่ดูดีไม่พอ ต้องดูว่าเรียกเครื่องมือถูก ใช้สิทธิ์ถูก และสร้างผลข้างเคียงตามที่ตั้งใจหรือไม่ ในแล็บนี้ evaluation, policy, pipeline และ trace ช่วยกันคนละด้าน

Runtime

สภาพแวดล้อมที่รันโปรแกรม

Amazon Bedrock AgentCore Runtime เป็นที่ให้โค้ด agent ทำงานและรับคำขอจากภายนอก ไม่ใช่ตัวโมเดลเพียงอย่างเดียว ตัวอย่างคือ support agent ที่รับคำถามเรื่องคืนเงินแล้วตัดสินใจว่าจะเรียกเครื่องมือใด

Endpoint / qualifier

ปลายทางและตัวเลือกปลายทาง

Endpoint อ้างอิง Runtime version ที่ต้องการเรียก ส่วน qualifier ใช้ระบุปลายทางในการ invocation ตาม API ที่ใช้ ในแล็บมี dev, staging, prod แต่ชื่อไม่ได้พิสูจน์ว่าชี้ version เดียวกันหรืออยู่คนละบัญชี ต้องตรวจการผูก version ของแต่ละ endpoint

Session

กลุ่มการสนทนาที่เกี่ยวข้องกัน

Session ใช้เชื่อมการโต้ตอบของผู้ใช้ในบริบทหนึ่ง อาจมีหลายคำขอและหลาย trace การประเมิน session ต้องเลือก session ของ invocation ที่ต้องการจริง ไม่หยิบค่าจากการลอง dev ไปประเมินว่าเป็น prod

Gateway

ทางผ่านไปยังเครื่องมือ

AgentCore Gateway ช่วยให้ agent เข้าถึงเครื่องมือผ่านจุดเชื่อมที่จัดการได้ ในโจทย์นี้ issue_refund มีเส้นทางผ่าน Gateway ไป Lambda ต้องตรวจว่าคำขอที่สงสัยผ่าน Gateway ตัวที่ผูก policy จริง ไม่สรุปจากแผนภาพอย่างเดียว

Tool / target

งานที่เรียกและปลายทางที่ผูกไว้

Tool คือความสามารถ เช่น issue_refund ส่วน target คือการเชื่อมปลายทางที่ Gateway ใช้ให้บริการเครื่องมือ เครื่องมือที่ชื่อคล้ายกันอาจมาจากคนละ target ได้ จึงต้องดูชื่อ action และ target ที่ปรากฏในคำขอจริง

Request interceptor

ตัวดักและปรับคำขอก่อนส่งต่อ

เป็นส่วนที่อ่าน ตรวจ หรือเติมข้อมูลในคำขอ ตัวอย่างผู้ใช้พบ log ว่าเติม order_total_cents=25000 ให้ ORD-1004 แต่ log ตรงนี้ยังไม่พิสูจน์ว่าข้อมูลถึง policy evaluation ด้วยชนิดและโครงสร้างที่ถูกต้อง และลำดับเทียบกับ policy ต้องยืนยันในเส้นทางแล็บ

Cedar policy

กฎตัดสินสิทธิ์ที่เขียนด้วยภาษา Cedar

ใช้ระบุว่าใครทำ action ใดกับ resource ใดได้ภายใต้เงื่อนไขใด โจทย์นี้ต้องการห้าม issue_refund เมื่อ context.input.order_total_cents > 10000 การมีเงื่อนไขถูกต้องยังต้องตรวจว่า action/resource/context ตรงคำขอที่นำมาตัดสิน

ACTIVE

สถานะที่เห็นบน policy

ในบริบทที่ผู้ใช้รายงาน ยืนยันได้ว่า policy แสดง ACTIVE ณ ตอนนั้น ต้องตรวจชื่อ field และ resource ที่หน้าจอหมายถึงด้วย ไม่ใช่ผล DENY ของทุกคำขอ และไม่ใช่หลักฐานว่าทดสอบเคส $250 ผ่านแล้ว

ENFORCE

โหมดบังคับใช้การตัดสิน

บอกว่า Gateway ถูกตั้งให้บังคับใช้ผล policy ตาม configuration นั้น ต่างจากการดูหรือบันทึกผลอย่างเดียว แต่ยังต้องพิสูจน์ว่าคำขอเป้าหมายวิ่งผ่านตัวนี้และ policy ที่เกี่ยวข้องถูกประเมินจริง

READY

ทรัพยากรอยู่ในสถานะพร้อม

เป็นสถานะความพร้อมของ resource ที่หน้าจอแสดง ในข้อมูลนี้เป็น Gateway READY ไม่ใช่การรับรองว่ากฎคืนเงินถูกต้อง การสร้างโครงสร้างสำเร็จและผลธุรกิจถูกต้องเป็นคนละหลักฐาน

Trace

ภาพเส้นทางของหนึ่งการทำงาน

Trace เชื่อมขั้นตอนที่เกี่ยวข้องของคำขอหนึ่งรอบเข้าด้วยกัน เช่นรับคำถาม เรียกโมเดล เรียก tool และตอบกลับ ใช้ตามหาว่าเคส ORD-1004 ไปถึงจุดใด แต่จะเห็นได้เท่าที่ระบบส่ง telemetry ไว้

Span

ช่วงงานย่อยใน trace

Span เป็นบันทึกของ operation หนึ่งช่วง พร้อมเวลาและข้อมูลประกอบ เช่นการเรียก tool หนึ่งครั้ง หลาย span เชื่อมกันเป็น trace ด้วยความสัมพันธ์และ identifiers การมีข้อความ log ธรรมดาไม่ได้แปลว่ามี span ตามรูปแบบที่ evaluator รับ

Evaluation

การประเมินตามเกณฑ์

นำหลักฐานการทำงานมาให้ evaluator ให้ผลตามเกณฑ์ เช่นตอบตรงโจทย์หรือเลือก tool เหมาะสม ผลประเมินอ้างอิงข้อมูลและเกณฑ์ที่ใช้ ไม่ได้พิสูจน์ทุกความเสี่ยงของระบบ ถ้า invalid span(s) รอบนั้นยังไม่ใช่ผลประเมินที่สำเร็จ

Online evaluation

ประเมินจากการใช้งานที่เข้ามา

เป็นการตั้งค่าให้ประเมิน trace จากแหล่งข้อมูลที่เลือกระหว่างมีการใช้งาน อาจมีตัวกรองและสัดส่วน sampling ซึ่งต้องออกแบบให้เหมาะ การเข้าหน้า Create evaluation configuration ยังไม่เท่ากับสร้าง configuration และเริ่มได้ผลประเมินแล้ว

CI/CD pipeline

ชุดขั้นตอนตรวจและส่งต่อเวอร์ชัน

CI คือการรวมและตรวจการเปลี่ยนแปลง ส่วน CD ในงานนี้คือกระบวนการส่งเวอร์ชันผ่านด่านไปยังสภาพแวดล้อมถัดไป Pipeline ที่มี manual approval ยังต้องรอผู้มีสิทธิ์ตัดสิน EvalGate สำเร็จไม่ได้พิสูจน์ว่าเคส policy ที่มีปัญหาอยู่ในชุดทดสอบ

dev

ปลายทางเพื่อพัฒนา

ใช้ลองการเปลี่ยนแปลงและตรวจปัญหาตามการจัดสภาพแวดล้อมของทีม ไม่ควรถือว่าข้อมูลทุกอย่างใน dev ปลอดผลข้างเคียงอัตโนมัติ ในภาพรายงาน เคส $250 ยังได้คำตอบ Refund processed บน dev

staging

ปลายทางทดสอบก่อน prod

ใช้ตรวจเวอร์ชันที่จะนำไปใช้งานต่อในสภาพแวดล้อมก่อน production ชื่อ staging ไม่รับรองว่าเหมือน prod ทุกค่า ในรายงาน PromoteToStaging สำเร็จ แต่เคส $250 ยังมีคำตอบผิดจากที่คาดบน staging

prod

ปลายทางใช้งานจริงตามชื่อที่ทีมกำหนด

ต้องตรวจว่า endpoint ชี้ version ใดจริงก่อนอธิบายพฤติกรรม การมี invocation prod ไม่ใช่หลักฐานว่า pipeline รอบล่าสุดได้โปรโมตแล้ว ในข้อมูลนี้ prod ปฏิเสธ ORD-1002 เพราะคำตอบระบุว่าส่งแล้ว 45 วัน

Observability

ความสามารถในการเข้าใจระบบจากหลักฐาน

ใช้ log, metric และ trace ร่วมกันเพื่ออธิบายว่าเกิดอะไรที่ชั้นใด Log interceptor, policy decision และ Lambda result ตอบคำถามคนละข้อ จึงควรจับคู่ให้เป็นคำขอเดียวกันก่อนสรุปสาเหตุ

Promotion

การเลื่อนเวอร์ชันไปปลายทางถัดไป

คือการนำเวอร์ชันที่กำหนดผ่านด่านไปใช้งานในสภาพแวดล้อมถัดไป ไม่ใช่แค่เรียก endpoint นั้นแล้วมีคำตอบ ต้องดู execution ของ pipeline และ version mapping ณ เวลาที่เกี่ยวข้อง

CloudFormation stack

ชุดทรัพยากรที่จัดการด้วยแม่แบบ

Stack success บอกว่ากระบวนการสร้างหรือปรับทรัพยากรเสร็จตามสถานะของ stack ไม่ได้ทดสอบคำขอคืนเงินให้โดยอัตโนมัติ ในกรณีนี้แยก “stack สร้างสำเร็จ” ออกจาก “policy บล็อก $250 ได้” เสมอ
