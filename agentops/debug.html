แก้ปัญหาจากหลักฐานทีละชั้น

นี่คือแผนตรวจสอบ ไม่ใช่การยืนยันว่าสาเหตุใดเกิดขึ้นแล้ว

ขอบเขตหลักฐาน บทเรียนอธิบายแนวคิดด้วยตัวอย่างสมมติ ส่วนผลทดลองเดิมในหน้าแก้ปัญหาและบทพูดอิงคำบอกเล่าจากภาพ ไม่ใช่สถานะ AWS ล่าสุด

แยกข้อสันนิษฐานออกจากหลักฐาน

ข้อสันนิษฐาน · ยังไม่ยืนยัน

อาจใช้คนละ target, context อาจไม่ถึง policy, หรือ agent อาจเล่าผลสำเร็จทั้งที่ tool ไม่สำเร็จ — ทั้งหมดเป็นสมมติฐาน ไม่ใช่สิ่งที่ตรวจพบแล้ว

วิธีคัดออกคือจับคู่คำขอเดียวกันกับ tool call → payload → decision → tool result ก่อนเปลี่ยน configuration

ติ๊กหมายถึง “อ่านและเตรียมตรวจแล้ว” ไม่ใช่การยืนยันว่าแก้ปัญหาหรือ AWS ผ่านการทดสอบ

ปัญหา 01

$250 ยังตอบว่าคืนเงินแล้ว

ACTIVE/ENFORCE เป็น configuration ต้องตามถึง decision ของคำขอเดียวกัน Refund processed ยังไม่ใช่หลักฐานธุรกรรม

  1. เริ่มจาก endpoint, version, เวลา และ session/trace ในพื้นที่ AWS ของแล็บ จับคู่ข้อความ Refund processed กับคำขอเดียวกันให้ได้

    หลักฐานที่หา / ข้อควรแยก

    ต้องได้เส้นทางเดียวกัน ไม่ใช้ log interceptor คนละรอบมาประกอบ แล้วถามว่ามี tool result จริงหรือเป็นเพียงข้อความ agent

  2. หา tool call ของ issue_refund ว่าชื่อเต็ม/action และ target ใดถูกเรียก มีการเรียกตรงหรือเส้นทางอื่นหรือไม่

    หลักฐานที่หา / ข้อควรแยก

    นี่คือสมมติฐานให้ตรวจ ไม่ใช่ข้อสรุปว่า agent ข้าม Gateway

  3. เทียบ Gateway ของคำขอกับ policy engine/configuration ที่แสดง ENFORCE และ policy ที่ตั้งใจใช้

    หลักฐานที่หา / ข้อควรแยก

    ACTIVE/ENFORCE ของทรัพยากรคนละตัวไม่ตอบคำถามนี้ ตรวจชื่อ resource ในระบบจริงโดยไม่คัด identifiers มาลงเว็บ

  4. ตรวจ principal/action/resource และชื่อ tool ที่อยู่ในคำขอจริงเทียบกับกฎ รวมถึง policy อื่นที่เกี่ยวข้อง

    หลักฐานที่หา / ข้อควรแยก

    อย่าคัดตัวอย่าง Cedar ที่เดา ARN หรือ action แล้วถือว่าเป็นกฎแก้ปัญหา ขอผู้สอนช่วยเทียบ schema

  5. ตรวจผล interceptor ที่ส่งต่อจริงว่ามี order_total_cents เป็นตัวเลข 25000 ณ path ที่ policy อ่าน ไม่ใช่ string หรือ field ที่ถูกตัดออก

    หลักฐานที่หา / ข้อควรแยก

    log ว่าเติมแล้วไม่เท่ากับ policy เห็นแล้ว ยืนยันลำดับ interceptor/policy ของแล็บด้วย ข้อมูล missing หรือ type mismatch ต้องตรวจ ไม่เดาพฤติกรรม

  6. ถ้า Gateway tracing เปิดอยู่ ให้หา authorization decision, reason, determining/mismatched policies ของคำขอเดียวกัน

    หลักฐานที่หา / ข้อควรแยก

    เอกสาร AWS อธิบาย span fields สำหรับ ALLOW/DENY อย่าตีความไม่พบ log ว่า ALLOW เพราะอาจดูคนละแหล่งหรือยังไม่มี telemetry

  7. เทียบ decision กับ Lambda invocation/tool result และข้อมูลธุรกรรมจำลองของแล็บถ้ามีสิทธิ์อ่าน

    หลักฐานที่หา / ข้อควรแยก

    ถ้า DENY แต่ agent พูดสำเร็จอาจเป็นการรายงานผลผิด ต้องมีหลักฐานก่อน ถ้า ALLOW ให้ย้อนตรวจ scope/context ไม่สรุปทันที

  8. วาง test matrix สำหรับ 9999, 10000, 10001 และ 25000 cents รวมกรณี field หาย/ชนิดผิดใน sandbox ของ workshop

    หลักฐานที่หา / ข้อควรแยก

    >10000 ไม่รวมเท่ากับ 10000 กฎนี้ใช้ order total ตามโจทย์ ไม่เดาว่าเป็นจำนวนเงินคืนบางส่วน เว็บไซต์นี้ไม่รัน tests บน AWS

ตัวอย่าง field ของ decision

เอกสาร AWS ระบุ aws.agentcore.policy.authorization_decision, aws.agentcore.policy.authorization_reason และ aws.agentcore.policy.mismatched_policies เมื่อมี Gateway traces ที่เกี่ยวข้อง เทียบคำขอเป้าหมาย ไม่ใช้ metric รวมแทนหลักฐานหนึ่งคำขอ

เอกสารต้นฉบับAWS · Policy decision spans ↗AWS · Policy enforcement modes ↗
ปัญหา 02

ValidationException: invalid span(s)

Trace คือเส้นทางหนึ่งรอบ span คือช่วงงานย่อย ต้องส่งข้อมูลที่ evaluator รองรับ Error นี้ไม่บอกสาเหตุเฉพาะและไม่ใช่คะแนนคุณภาพ

  1. เลือก prod invocation จริงที่ต้องการ ไม่ใช้ session จาก dev/staging หรือค่าเก่าใน shell

    หลักฐานที่หา / ข้อควรแยก

    เตรียมเวลา endpoint/version และ session ในพื้นที่แล็บเท่านั้น เว็บนี้ไม่รับ identifiers จริง

  2. ตรวจ trace/spans ว่าปรากฏครบและอยู่ในช่วงเวลาที่เลือกแล้วหรือยัง

    หลักฐานที่หา / ข้อควรแยก

    Telemetry อาจยังมาไม่ครบ แต่เป็นเพียงจุดตรวจ ไม่ฟันธงว่าเกิดจากการรอไม่พอ

  3. เทียบ endpoint, service name, region และ log group ที่สคริปต์ query กับแหล่งที่ Runtime ส่งข้อมูลจริง

    หลักฐานที่หา / ข้อควรแยก

    อย่าเดาว่าทุกแล็บใช้ log group เดียว เอกสารและ configuration อาจต่างตามเวอร์ชัน

  4. ดูว่าสคริปต์ส่ง sessionSpans ที่ evaluator รองรับ มีโครงสร้าง/attributes ที่จำเป็นและไม่ใช่ wrapper ของ log event หรือ JSON string ผิดชั้น

    หลักฐานที่หา / ข้อควรแยก

    เปิดคู่มือ schema/framework ของแล็บเทียบ ข้อความ invalid span(s) อย่างเดียวบอก field ที่ผิดไม่ได้

  5. ถ้าเลือก trace/span เฉพาะ ต้องอยู่ในชุด input จริง ตรวจชนิด evaluator และขอบเขต session/trace/tool ที่รองรับ

    หลักฐานที่หา / ข้อควรแยก

    อย่านำ session ID ไปแทน trace ID หรือ span ID ชื่อเหล่านี้มีหน้าที่ต่างกัน

  6. เก็บ ValidationException แบบเต็มที่ตัดข้อมูลลับแล้ว เทียบเวอร์ชันสคริปต์/SDK กับ workshop

    หลักฐานที่หา / ข้อควรแยก

    รอบที่ validation ไม่ผ่านไม่มีคะแนนสำเร็จ ยังสรุปคุณภาพ agent จากรอบนี้ไม่ได้

  7. ใช้ span ตัวอย่างที่ตัดข้อมูลระบุตัวตนในช่องทางที่อนุญาต เทียบกับตัวอย่าง known-good ของ workshop

    หลักฐานที่หา / ข้อควรแยก

    ยังไม่ต้องสร้าง online evaluation เพื่อหวังแก้ on-demand error เพราะเป็นคนละขั้น

เอกสารต้นฉบับAWS · Evaluate input/target ↗AWS · On-demand evaluation ↗AWS · Online evaluation configuration ↗
ปัญหา 03

NEW_VERSION ว่างใน shell

ตัวแปรเป็นค่าของ shell ที่ใช้อยู่ เปิดหน้าต่างใหม่หรือข้ามขั้นกำหนดค่าอาจไม่มีค่า ครั้งที่เล่าจึงส่ง variables[1].value ว่าง ควรตรวจค่าและแหล่ง version ก่อนประกอบคำสั่ง

Terminal · Bash / zsh · อ่านตัวแปรเท่านั้น
if [ -z "${NEW_VERSION:-}" ]; then
  printf "%s\n" "NEW_VERSION is empty. Check the intended version first."
else
  printf "NEW_VERSION=%s\n" "$NEW_VERSION"
  printf "%s\n" "Value exists; verify it matches the intended runtime version."
fi

${NEW_VERSION:-}
อ่าน NEW_VERSION ถ้ายังไม่ตั้งใช้ค่าว่าง รองรับ shell ที่ตรวจตัวแปร unset
-z
ทดสอบว่าข้อความว่าง ถ้าใช่ให้หยุดตรวจค่า
คำพูดรอบ $...
รักษาค่าเป็น argument เดียว ไม่ได้ไปดึง version จาก AWS
ถ้ามีค่าแล้ว
แค่ไม่ว่าง ต้องตรวจว่าตรง version ที่ต้องการ อย่าเดาหมายเลข

ตัวอย่างไม่ตั้ง version ไม่เริ่ม pipeline ไม่ approve และไม่ deploy
