ภาพรวม

DevOps ช่วยให้การเปลี่ยนแปลงจากโจทย์งานไปถึงผู้ใช้เป็นเส้นทางที่มองเห็น ตรวจได้ และรับผิดชอบร่วมกัน ส่วน Environment Strategy คือการจัดพื้นที่ DEV, UAT และ PROD ให้เหมาะกับวัตถุประสงค์ ข้อมูล สิทธิ์ และความเสี่ยง

จำสั้น ๆ: Change → Review → Test → UAT → Approve → PROD → Observe

ศัพท์เทคนิคที่ใช้บนสไลด์

Repo คือที่เก็บ code และประวัติ; branch คือทางแยก code; commit คือจุดบันทึก; Pull Request (PR) คือคำขอให้ตรวจและรวม code; merge คือการรวม branch; pipeline คือขั้นตอนอัตโนมัติ; deploy คือนำรุ่นไปติดตั้ง; release คือเปิดให้ใช้งาน; rollback คือกลับไปใช้รุ่นก่อนหน้า

CI คือการรวมและตรวจ code บ่อย ๆ ส่วน CD อาจหมายถึง Continuous Delivery ที่เตรียมรุ่นพร้อมส่งและมีจุดอนุมัติ หรือ Continuous Deployment ที่ปล่อยอัตโนมัติตามเงื่อนไข

ตัวอย่างสมมติ: เพิ่มช่องในแบบฟอร์ม

  1. เขียนโจทย์และ acceptance criteria ใน ticket ถ้ามี Jira
  2. สร้าง feature branch ใน Bitbucket แก้ code และ commit
  3. เปิด PR ให้ reviewer ดู diff และให้ pipeline รัน build/test
  4. นำรุ่นไป DEV เพื่อลอง แล้ว UAT ให้เจ้าของงานตรวจตามเกณฑ์
  5. ผ่าน approval gate ก่อนผู้มีสิทธิ์นำรุ่นไป PROD
  6. ดู logs/metrics หลังปล่อย และเตรียม rollback หรือ roll forward หากมีปัญหา

Jira, Bitbucket, pipeline และ AWS เป็นตัวอย่างเครื่องมือที่อาจอยู่ใน flow เดียวกัน แต่ต้องตรวจระบบจริงก่อนระบุว่าองค์กรใช้ครบหรือเชื่อมกันอย่างไร

Branch ต่างจาก environment อย่างไร

Branch อยู่ในระบบเก็บ code เช่น Bitbucket ส่วน environment คือแอปที่รันอยู่พร้อม config, data และ access เช่น DEV/UAT/PROD บน AWS หรือแพลตฟอร์มอื่น การ merge เข้า main จึงไม่จำเป็นต้อง deploy PROD ทันที ขึ้นกับ pipeline และ release policy

สิทธิ์และการเปลี่ยนโครงสร้าง

IAM ใช้กำหนดว่าใครหรือบริการใดทำอะไรได้บน AWS ผู้ฝึกงานอาจช่วยทำ PR และเตรียมหลักฐานทดสอบ โดยไม่จำเป็นต้องมีสิทธิ์ deploy PROD IaC เช่น Terraform เก็บแบบแปลนโครงสร้าง cloud เป็น code ก่อนนำไปใช้ควรตรวจแผน ผลกระทบ และสิทธิ์ของผู้อนุมัติ

คำถาม–คำตอบที่อาจเจอ (กดเปิด)

Merge เข้า main แล้วขึ้น PROD เลยไหม?

สรุปไม่ได้จนกว่าจะเห็น pipeline และ release policy บางทีม deploy อัตโนมัติ บางทีมต้องผ่าน UAT และ approval gate ก่อน

Test ผ่านแล้วทำไมต้องมี UAT?

Automated test ตรวจเฉพาะกรณีที่เขียนไว้ UAT ให้เจ้าของงานยืนยันว่าใช้งานได้ตรงตาม acceptance criteria

DEV/UAT/PROD ต้องแยก AWS account ไหม?

ขึ้นกับข้อกำหนดด้านความปลอดภัย ต้นทุน และความเสี่ยงขององค์กร อย่างน้อยต้องแยก config, data และสิทธิ์ให้เหมาะสม ไม่ควรฟันธงวิธีตั้งค่าจากข้อมูลที่เรามี

Branching strategy แบบไหนเหมาะ?

แนวทางตัวอย่างคือ main ที่ป้องกัน, feature branch อายุสั้น, PR และ checks ก่อน merge แต่ต้องปรับให้เข้ากับวิธีปล่อยงานของทีม

ถ้า deploy แล้วพัง ทำอะไร?

ดูผลกระทบจาก logs/metrics แล้วตัดสินใจ rollback ไปใช้รุ่นก่อนหรือ roll forward ด้วยรุ่นที่แก้แล้ว ระวังว่าการย้อนแอปไม่ได้ย้อนข้อมูลฐานข้อมูลเสมอ

ถ้าไม่มีสิทธิ์ deploy จะช่วยได้อย่างไร?

ช่วยทำ PR, test evidence, release note และขั้นตอนตรวจรับ แล้วให้ผู้มีสิทธิ์ดำเนินการตาม policy

ถ้าถูกถามรายละเอียดระบบจริงที่ไม่ทราบ?

“ผมยังไม่ได้ตรวจการตั้งค่าของโปรเจกต์นั้นครับ ตัวอย่างวันนี้เป็นหลักคิดและจุดที่ควรดูเมื่อนำไปใช้จริง”
