02 / 08 · 2 นาที

โจทย์สมมติ: เพิ่มช่องในเว็บฟอร์ม

  • นักพัฒนาแก้โค้ดเสร็จ
  • เจ้าของงานต้องตรวจว่าตรงความต้องการ
  • ผู้ใช้จริงต้องได้รุ่นที่ผ่านการตรวจ
  • ถ้ามีปัญหา ต้องรู้ว่าจะทำอย่างไร

โน้ตพูด · ปัญหาที่ DevOps ช่วยจัดการ

ประมาณ 2 นาที

“สมมติทีมทำเว็บฟอร์มภายใน แล้วเพิ่มช่องประเภทคำขอ ต่อให้เขียนโค้ดเสร็จ ก็ยังมีคำถามว่าใครตรวจว่าใช้ได้ ใครยืนยันว่าตรงโจทย์ และใครปล่อยให้ผู้ใช้จริง ถ้ารุ่นใหม่มีปัญหา เราต้องตามให้ได้ว่ารุ่นไหนถูกปล่อยและแก้อย่างไร นี่คือเหตุผลที่ต้องมองเส้นทางส่งงานทั้งเส้น”

03 / 08 · 2 นาที

DevOps = ทำให้การส่งงานเชื่อมกัน

พัฒนา→ตรวจ→ปล่อย→ติดตาม

คน ขั้นตอน และเครื่องมือช่วยให้เปลี่ยนแปลงได้อย่างตรวจสอบได้

โน้ตพูด · DevOps และ CI/CD

ประมาณ 2 นาที

“DevOps ย่อจาก Development กับ Operations แนวคิดคือเชื่อมการพัฒนาและการดูแลระบบเข้าด้วยกัน เช่น ตกลงว่าใครตรวจ ทดสอบอะไร ปล่อยอย่างไร และดูผลหลังปล่อย เครื่องมือช่วยทำซ้ำขั้นตอนนี้ CI คือรวมงานและตรวจบ่อย ๆ ส่วน CD เกี่ยวกับการเตรียมปล่อยหรือปล่อยงาน โดย production อาจมีคนอนุมัติก่อน ไม่จำเป็นต้องอัตโนมัติทั้งหมด”

04 / 08 · 3 นาที

Environment: รันที่ไหน ใครใช้

  • DEV — นักพัฒนาลองแก้และทดสอบ
  • UAT — เจ้าของงานตรวจว่าตรงโจทย์
  • PROD — ผู้ใช้จริงใช้งาน

โน้ตพูด · Environment

ประมาณ 3 นาที

“Environment คือพื้นที่ที่แอปรัน พร้อมค่าตั้งและบริการที่ต้องใช้ ใน DEV เราลองแก้และทดสอบช่องใหม่ ใน UAT เจ้าของงานลองขั้นตอนจริงว่าชื่อช่องและการบันทึกตรงโจทย์หรือไม่ จากนั้นจึงปล่อยสู่ PROD ที่ผู้ใช้จริงใช้ การมี UAT ช่วยตรวจความต้องการทางธุรกิจ แต่แต่ละระบบต้องเลือกรูปแบบตามความเสี่ยงและค่าใช้จ่าย Config เช่น URL ควรแยกตามพื้นที่ ส่วน token หรือ password เป็น secret ต้องเก็บตามนโยบายองค์กร”

ถ้าถูกถาม: UAT ไม่จำเป็นว่าต้องเป็นสำเนา PROD ทุกอย่าง แต่ต้องเหมาะกับสิ่งที่ต้องการตรวจ

05 / 08 · 3 นาที

Branching: แยกงานก่อนรวม

main→feature branch→PR→review + merge

ใน Bitbucket, PR เป็นจุดให้ทีมเห็นและตรวจการเปลี่ยนแปลง

โน้ตพูด · Branch และ Pull Request

ประมาณ 3 นาที

“Git เก็บประวัติการแก้โค้ด Branch คือเส้นทางแยกสำหรับทำงานหนึ่งเรื่อง สมมติผมเพิ่มช่องประเภทคำขอ ผมแยก feature branch พอเสร็จเปิด PR ใน Bitbucket อธิบายว่าทำอะไรและทดสอบอย่างไร คน review แล้ว merge ตามกติกาทีม Branch protection อาจบังคับ reviewer หรือ pipeline ก่อน merge จุดสำคัญคือ branch แยกโค้ด แต่ environment คือที่รันแอป สองอย่างนี้ไม่ใช่สิ่งเดียวกัน และ merge เข้า main ก็ไม่ได้แปลว่า deploy production ทันทีเสมอไป”

06 / 08 · 2 นาที

ประกอบเป็นเส้นทางเดียว

Branch + PR→Test→UAT→Approve→PROD

หลังปล่อย: ตรวจผล และเตรียมวิธีแก้หรือย้อนรุ่น

โน้ตพูด · เส้นทางส่งงาน

ประมาณ 2 นาที

“ภาพนี้เป็นตัวอย่าง ไม่ใช่ workflow ที่ยืนยันแล้วของบริษัท หลัง PR และ test เรานำรุ่นที่ระบุได้ไป UAT ให้เจ้าของงานตรวจ จากนั้นผู้มีสิทธิ์อนุมัติและปล่อย production หลังปล่อยต้องดู error หรือ feedback ถ้ามีปัญหาอาจ rollback ไปใช้รุ่นก่อน แต่ถ้าฐานข้อมูลเปลี่ยนด้วย การย้อนแอปอย่างเดียวอาจไม่พอ จึงต้องวางแผนตามระบบจริง”

07 / 08 · 1 นาที

นำไปใช้กับทีม: เริ่มจากคำถาม

  • ใคร review, ตรวจรับ และอนุมัติการปล่อย?
  • งานแบบไหนต้องมี UAT?
  • ใครดูแล AWS และสิทธิ์ deploy?
  • ติดปัญหาเครื่องหรือเครือข่าย ติดต่อใคร?

โน้ตพูด · บริบททีม

ประมาณ 1 นาที

“ทีมเราใช้ Bitbucket และอาจมีงานที่ขึ้น AWS สิ่งที่ผมอยากชวนคุยคือใครทำหน้าที่แต่ละช่วง โดยเฉพาะเมื่อสิทธิ์ของทีมฝึกงานมีข้อจำกัด ส่วนปัญหาจากเครื่องหรือเครือข่ายองค์กร เช่นที่อาจเกี่ยวกับ Zscaler ควรเก็บ error และขั้นตอนที่ทำไปถามผู้ดูแล ไม่เดาสาเหตุหรือแก้การตั้งค่าเอง”

08 / 08 · 1 นาที

จำ 3 ประโยคนี้

  • DevOps เชื่อมการสร้างกับการดูแลระบบ
  • Environment บอกว่าระบบรันที่ไหนและใครใช้
  • Branch + PR ช่วยจัดการและตรวจการเปลี่ยนโค้ด

วิธีใช้จริง ต้องตกลงกับเจ้าของระบบและผู้มีสิทธิ์

โน้ตพูด · ปิด

ประมาณ 1 นาที

“สรุปคือ DevOps ช่วยให้การเปลี่ยนแปลงมีเส้นทางตรวจสอบได้ Environment ช่วยแยกช่วงทดลอง ตรวจรับ และใช้งานจริง ส่วน branch กับ PR ช่วยให้ทีมตรวจโค้ดก่อนรวม แนวทางที่เหมาะกับงานเราต้องตกลงเรื่องความเสี่ยง สิทธิ์ และผู้รับผิดชอบร่วมกัน ขอบคุณครับ”

หากมีคำถามเชิงระบบจริงที่ไม่ทราบ: “ส่วนนี้ผมยังไม่มีข้อมูลยืนยัน หลักทั่วไปคือ… และควรตรวจกับเจ้าของระบบก่อนใช้จริงครับ”
