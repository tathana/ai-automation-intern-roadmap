ตั้งขอบเขต

“สวัสดีครับ ผม Thanaphat วันนี้จะเล่าเรื่อง DevOps และ Environment Strategy โดยมีสามคำสำคัญคือ DevOps, environment และ branching strategy ครับ”

“ผมจะใช้ระบบสมมติหนึ่งระบบเป็นตัวอย่างตลอดทาง เพราะอยากให้เห็นว่าการเปลี่ยนโค้ดหนึ่งครั้งเดินทางจากเครื่องคนพัฒนาไปถึงผู้ใช้จริงได้อย่างไร โดยไม่ได้ประเมินวิธีทำงานของโปรเจกต์ใดในทีม”

“ตอนท้ายผมจะชวนดูว่าถ้าจะนำหลักการนี้มาใช้กับงานเรา ต้องรู้เรื่องสิทธิ์ ผู้อนุมัติ และขั้นตอนตรวจรับอะไรบ้างครับ”

หากไม่มีการแชร์จอ: พูดได้ตรง ๆ ว่า “ผมขอเล่าเป็นภาพเส้นทางหนึ่งงานนะครับ”

02 / 08 · ประมาณ 2 นาที · ปัญหา

โค้ดเสร็จ ยังไม่เท่ากับงานถึงผู้ใช้

“สมมติเรามีเว็บฟอร์มภายในที่พนักงานใช้ส่งคำขอ และมีโจทย์ให้เพิ่มช่อง ‘ประเภทคำขอ’ คนพัฒนาแก้หน้าฟอร์มและโค้ดบันทึกข้อมูลเสร็จแล้ว แต่เรายังตอบไม่ได้ทันทีว่าควรปล่อยให้ทุกคนใช้เลยหรือเปล่า”

“คำถามแรกคือมันทำงานถูกไหม เช่น เลือกประเภทแล้วบันทึกได้จริงหรือไม่ คำถามที่สองคือมันตรงกระบวนการของเจ้าของงานไหม ชื่อประเภทถูกต้องหรือมีขั้นอนุมัติที่ต้องเปลี่ยนด้วย คำถามที่สามคือใครมีสิทธิ์นำรุ่นนี้ขึ้นระบบจริง และถ้าขึ้นแล้วเกิด error เราจะรู้ได้อย่างไรว่า error เริ่มจากรุ่นไหน”

“ดังนั้นการเขียนโค้ดเป็นเพียงต้นทาง งานหนึ่งชิ้นต้องผ่านการตรวจ ทดลอง ปล่อย และติดตามผล ความเสี่ยงในแต่ละช่วงไม่เหมือนกัน จึงต้องมีคนและขั้นตอนรับผิดชอบให้ชัดครับ”

03 / 08 · ประมาณ 2 นาที · DevOps

เชื่อม development กับ operations

“DevOps มาจาก Development กับ Operations ผมเข้าใจว่าเป็นแนวทางทำให้คนสร้างระบบกับคนดูแลระบบที่ใช้งานจริงทำงานต่อเนื่องกัน ตั้งแต่รู้โจทย์ พัฒนา ตรวจ ปล่อย จนถึงดูผลหลังปล่อย”

“ตัวอย่างที่จับต้องได้คือเก็บโค้ดใน Git เพื่อรู้ว่ารุ่นไหนเปลี่ยนอะไร เปิด Pull Request หรือ PR ให้ reviewer ตรวจ ใช้ CI pipeline รัน test ซ้ำได้ และระบุว่าใครเป็นคนอนุมัติที่ approval gate ก่อน release หากเกิดปัญหาเราจะตามกลับไปได้ว่ารุ่นไหนถูกปล่อยและใครรับช่วงแก้ไข”

“ศัพท์ CI หมายถึงการรวมงานและตรวจการเปลี่ยนแปลงบ่อย ๆ เช่น PR แล้ว test อัตโนมัติ ส่วน CD มีทั้ง Continuous Delivery คือเตรียมให้พร้อมปล่อยโดยอาจมีคนอนุมัติ และ Continuous Deployment คือปล่อยอัตโนมัติเมื่อผ่านเงื่อนไข การทำ DevOps จึงไม่ได้บังคับว่าต้องให้ production deploy อัตโนมัติทุกครั้งครับ”

ถ้าพูดเร็ว ให้หยุดครึ่งวินาทีหลังคำว่า CI และ CD เพื่อให้คนฟังแยกสองเรื่องนี้ได้

04 / 08 · ประมาณ 3 นาที · Environment

ระบบรันที่ไหน และใครเป็นผู้ใช้

“Environment คือพื้นที่ที่แอปทำงาน พร้อมค่าตั้งและบริการที่เกี่ยวข้อง ผมจะพูดสามระดับที่โจทย์ให้มา คือ DEV, UAT และ PROD”

“DEV environment เป็นที่คนพัฒนาแก้และลองพฤติกรรมใหม่ สำหรับเว็บฟอร์มสมมติ เราลองว่าช่องประเภทคำขอแสดงและบันทึกได้ UAT ย่อจาก User Acceptance Testing เป็นที่ให้เจ้าของงานหรือผู้ใช้ที่เกี่ยวข้องตรวจว่าใช้งานตรงความต้องการจริง เช่น ประเภทที่เลือกตรงกับภาษาของฝ่ายงานและขั้นอนุมัติถูกต้อง PROD คือพื้นที่ที่ผู้ใช้จริงใช้งาน การเปลี่ยนแปลงจึงมีผลกระทบสูงกว่า”

“ประเด็นสำคัญคือสามชื่อนี้ต้องมีความหมายทางปฏิบัติ ไม่ใช่แค่ชื่อโฟลเดอร์ เราควรรู้ว่าแต่ละที่ใช้ข้อมูลชุดไหน ใครเข้าถึงได้ และค่าตั้งต่างกันอย่างไร เช่น URL ของ API หรือฐานข้อมูล ส่วนรหัสผ่านและ token เป็น secrets ควรเก็บในวิธีที่องค์กรอนุญาต ไม่ใส่ใน repository”

“UAT ควรใกล้เคียง production ในส่วนที่ใช้ตรวจงาน แต่ไม่จำเป็นต้องมีขนาดเท่ากันทุกด้าน ถ้า UAT ใช้ข้อมูลจำลองขนาดเล็ก มันอาจพิสูจน์ workflow ได้ แต่ยังไม่พิสูจน์ว่าจะรับข้อมูลจำนวนมากได้ การแยก environment ยังมีต้นทุนและคนดูแล จึงต้องเลือกให้เหมาะกับความเสี่ยงของระบบครับ”

05 / 08 · ประมาณ 3 นาที · Branching

แยกงานใน Git ก่อนรวมกลับ

“อีกด้านหนึ่งคือ branching strategy ซึ่งตอบคำถามว่าเราจัดการโค้ดที่หลายคนแก้พร้อมกันอย่างไร Branch คือเส้นทางประวัติโค้ดที่แยกออกมาทำงานหนึ่งเรื่อง สมมติผมจะเพิ่มช่องประเภทคำขอ ผมอาจเริ่มจาก branch ชื่อ feature/request-type”

“เมื่อแก้และทดสอบบนเครื่องแล้ว ผมเปิด PR ใน Bitbucket อธิบายว่าทำอะไร เหตุใดจึงทำ และทดสอบอย่างไร Reviewer จะ review ความเปลี่ยนแปลงและถามจุดที่ไม่ชัด หากทีมกำหนด merge checks อาจต้องผ่าน test หรือมีคนอนุมัติก่อน merge เข้า main”

“main เป็น branch หลักในตัวอย่างนี้ แต่การ merge เข้า main ไม่จำเป็นว่าโค้ดขึ้น production ทันที บางทีมรวมแล้ว deploy ไป UAT ก่อน บางทีมรอรอบ release จุดนี้ขึ้นกับ workflow จริง”

“สิ่งที่ผมอยากแยกให้ชัดคือ branch กับ environment เป็นคนละมิติ Branch บอกว่าโค้ดเปลี่ยนอะไร ส่วน environment บอกว่ารุ่นนั้นรันที่ไหน เราอาจนำ commit เดียวกันไปทดลองใน UAT แล้วค่อยปล่อย PROD ได้ และถ้า branch ค้างนานเกินไป การ merge กลับจะยากขึ้น จึงควรทำงานเป็นชิ้นเล็กและรวมบ่อยตามที่ทีมพร้อมครับ”

06 / 08 · ประมาณ 2 นาที · เส้นทางรวม

เชื่อม branch, test, UAT และ PROD

“ถ้าเอาทุกอย่างมารวมกัน เส้นทางหนึ่งที่เป็นไปได้คือรับโจทย์และเกณฑ์ตรวจรับก่อน จากนั้นทำ feature branch เปิด PR ให้คนตรวจและให้ CI รันทดสอบ เมื่อผ่านจึงรวมงาน และdeploy รุ่นที่ระบุได้ไป UAT”

“เจ้าของงานตรวจรับว่าแบบฟอร์มใหม่ตรงโจทย์หรือไม่ เมื่อผ่าน approval gate ผู้มีสิทธิ์จึง deploy ไป PROD หลัง deployment ต้อง monitor ผล เช่น error, งานที่ส่งไม่สำเร็จ หรือ feedback จากผู้ใช้”

“ก่อนปล่อยควรรู้ด้วยว่าถ้ามีปัญหาจะทำอย่างไร Rollback อาจหมายถึงนำแอปรุ่นก่อนกลับมา แต่ถ้ารุ่นใหม่เปลี่ยนฐานข้อมูลหรือข้อมูลที่เขียนไปแล้ว การย้อนแอปอย่างเดียวอาจไม่พอ เรื่องนี้ต้องวางแผนตามระบบจริง”

“เส้นทางนี้เป็นตัวอย่างเพื่ออธิบายความสัมพันธ์ของสามหัวข้อ ไม่ใช่ข้อสรุปว่าบริษัทเราทำขั้นตอนนี้อยู่แล้วครับ”

07 / 08 · ประมาณ 1 นาที · บริบททีม

นำหลักการไปใช้ ต้องรู้บทบาทก่อน

“ในทีมที่ใช้ Bitbucket เราเริ่มพูดเรื่อง branch, PR และ review บนเครื่องมือที่มีอยู่ได้ แต่ถ้างานต้อง deploy ขึ้น AWS ต้องทราบก่อนว่าใครเป็นเจ้าของ environment และใครมีสิทธิ์ปล่อย production นักศึกษาฝึกงานอาจเตรียม PR, test evidence และขั้นตอนตรวจรับ ส่วนการ deploy จริงอาจอยู่กับผู้ดูแล”

“หากติดปัญหาจากเครื่องหรือเครือข่ายองค์กร เช่นเข้าถึงบริการไม่ได้ สิ่งที่ช่วยทีม IT ได้คือข้อความ error เวลา และขั้นตอนที่ทำ เราไม่ควรสรุปสาเหตุจากการเห็นชื่อเครื่องมืออย่าง Zscaler เพียงอย่างเดียวครับ”

08 / 08 · ประมาณ 1 นาที · สรุป

สามเรื่องที่เชื่อมกัน

“สรุปสามประโยคครับ DevOps ช่วยให้ทีมรับผิดชอบเส้นทางจากพัฒนาไปจนถึงดูแลระบบ Environment ช่วยแยกพื้นที่ทดลอง ตรวจรับ และใช้งานจริง ส่วน branch กับ PR ช่วยจัดการและตรวจการเปลี่ยนแปลงของโค้ด”

“ถ้าจะนำไปใช้จริงกับงานทีม ผมคิดว่าคำถามแรกไม่ใช่เลือกเครื่องมือเพิ่ม แต่คือใคร review, ใครตรวจรับ, ใครอนุมัติ deploy, ระบบใดต้องมี UAT และถ้าเกิดปัญหาใครรับช่วงต่อครับ ขอบคุณครับ”

หลังจบ · เตรียมตอบคำถาม

คำตอบสั้นที่ใช้ได้

ทำไม CI ผ่านแล้วยังต้อง UAT?

CI ตรวจเงื่อนไขที่เราเขียนไว้ เช่น build และ test ส่วน UAT ช่วยให้เจ้าของงานตรวจว่าพฤติกรรมตรงความต้องการจริง

ต้องมีสาม environment ทุกระบบหรือไม่?

จำนวน environment ขึ้นกับผลกระทบ ค่าใช้จ่าย และวิธีตรวจรับ ควรระบุให้ชัดว่าทดสอบที่ไหนและใครอนุมัติก่อนผู้ใช้จริงได้รับการเปลี่ยนแปลง

Branch ชื่อ uat คือ UAT หรือไม่?

ไม่ครับ ชื่อ branch เป็นเรื่องของโค้ด UAT คือระบบที่รันให้ผู้ใช้ตรวจรับ ต้องมี deployment และค่าตั้งที่เหมาะกับการตรวจ

ทำไมไม่ deploy ตรงจาก laptop?

การใช้ขั้นตอนกลางช่วยให้รู้ว่าปล่อยรุ่นไหน ผ่าน test อะไร และทำซ้ำได้ แต่รูปแบบจริงต้องตามข้อกำหนดองค์กร

ถ้าถูกถามเรื่อง AWS architecture เฉพาะของทีม?

“ส่วนนี้ผมยังไม่มีข้อมูลยืนยันของระบบเรา หลักทั่วไปคือระบุเจ้าของ environment และสิทธิ์ deploy ก่อน แล้วควรตรวจรายละเอียดกับผู้ดูแลระบบครับ”

ถ้าเวลาหมดก่อน?

ข้ามรายละเอียด CI/CD ในช่วง 3 และตัวอย่าง rollback ในช่วง 6 แล้วใช้สรุปช่วง 8 ปิดให้ครบสามหัวข้อ
