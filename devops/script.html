01 / 08 · เปิดเรื่อง

ทำให้การเปลี่ยนแปลงไปถึงผู้ใช้ได้อย่างมั่นใจ

สวัสดีครับ วันนี้ผมจะเล่า DevOps & Environment Strategy โดยโฟกัสสามเรื่องที่เชื่อมกัน คือการ review code change การแยก environment และการควบคุม release ครับ

ผมจะใช้หลักการทั่วไปและตัวอย่างสมมติ ไม่ได้สรุป workflow ของโปรเจกต์ใดเป็นพิเศษ เป้าหมายคือให้เห็นว่าเปลี่ยนอะไร ใครตรวจ และใครมีสิทธิ์ปล่อยรุ่นไปใช้งานจริง

02 / 08 · ประมาณ 2 นาที

DevOps ในงานจริง

DevOps มาจาก Development กับ Operations ครับ เป็นวิธีทำให้การพัฒนาและการดูแลระบบเชื่อมกัน ตั้งแต่ทีมแก้ code ตรวจคุณภาพ ปล่อยใช้งาน ไปจนถึงดูผลหลัง release

สิ่งสำคัญคือ ownership ชัด ได้ feedback เร็ว และทำ checks ที่ทำซ้ำได้ เช่น CI pipeline

CI หรือ Continuous Integration เน้นรวมการเปลี่ยนแปลงและตรวจ ส่วน CD มีทั้ง Continuous Delivery ที่เตรียมให้พร้อมปล่อยโดยอาจมี manual approval และ Continuous Deployment ที่ปล่อยอัตโนมัติเมื่อผ่านเงื่อนไข

Manual approval เป็นส่วนหนึ่งของ Continuous Delivery ได้

03 / 08 · ประมาณ 3 นาที

DEV / UAT / PROD มี purpose คนละแบบ

Environment คือพื้นที่ที่ระบบรัน รวมถึง configuration, data และ access ที่ใช้ในพื้นที่นั้น DEV มีไว้ให้ dev ทดลองและรับ feedback เร็ว UAT ให้ owner ตรวจว่าผลตรง acceptance criteria หรือไม่ PROD คือระบบที่ผู้ใช้จริงใช้งาน จึงต้องจำกัดสิทธิ์และติดตามหลังปล่อย

UAT ควรคล้าย production ในส่วนที่จำเป็นต่อการตรวจ แต่ไม่จำเป็นต้องเหมือนทุกอย่าง การเพิ่ม environment มี cost และภาระดูแล จึงเลือกระดับให้เหมาะกับ risk

Configuration เช่น endpoint ต้องชี้ให้ถูก environment ส่วน secrets เช่น token หรือ password ไม่ควรฝังไว้ใน source code

04 / 08 · ประมาณ 3 นาที

Branching strategy: เล็ก แยกชัด รวมเร็ว

ใน Git, branch คือเส้นทาง code change ที่แยกไว้ทำงานหนึ่งเรื่อง สมมติทีมเพิ่ม field หนึ่งตัว ก็เปิด feature branch ที่สื่อถึงงานนั้น พอพร้อมตรวจให้เปิด PR ใน Bitbucket เพื่อให้ reviewer ดู diff เหตุผล และผลทดสอบ

CI checks สามารถรัน build หรือ test อัตโนมัติได้ ส่วน branch restrictions อาจกำหนดว่าต้องมี reviewer หรือ check ใดผ่านก่อน merge

แนวทางที่อธิบายง่ายคือ branch อายุสั้น เปิด PR แล้ว merge บ่อยพอควบคุมความขัดแย้ง กติกาจริงต้องตาม repository policy ที่ admin ตั้งไว้

Branch เก็บ code change; environment คือ runtime ที่ deploy ไป และการ merge เข้า main ไม่ได้แปลว่าขึ้น production เสมอไป

05 / 08 · ประมาณ 3 นาที

Release controls: ผ่าน checks ก่อน promote

Pipeline อาจเชื่อมตั้งแต่ commit, build, test ไปจนถึง UAT และ production แต่แต่ละระบบไม่จำเป็นต้อง automate ทุกขั้น และ approval gate อาจเป็น manual ตาม policy

ควรระบุให้ได้ว่ารุ่นไหนผ่าน test และรุ่นไหนกำลังจะปล่อย หาก build เป็น artifact ควร trace กลับไปยัง source version ได้ การ promote รุ่นที่รู้จักช่วยยืนยันว่ากำลังปล่อยสิ่งที่ตรวจแล้ว

การเปลี่ยน application code กับ infrastructure หรือ IaC อาจมี impact คนละแบบ ถ้าแก้ Terraform หรือ cloud resource ควร review ผลกระทบและใช้สิทธิ์ตามขั้นตอนที่องค์กรอนุมัติ

เตรียม rollback หรือ roll forward และคิดด้วยว่า database change ทำให้ย้อน app อย่างเดียวไม่ได้เสมอ หลัง deploy ให้ monitor อาการระบบครับ

06 / 08 · ประมาณ 1.5 นาที

Ownership & access ทำให้ workflow ใช้ได้จริง

การมีสิทธิ์จำกัดไม่ได้แปลว่าทีมไม่มีส่วนใน workflow คนพัฒนาเตรียม PR, test evidence และ release notes ได้ reviewer ตรวจ code, owner ตรวจ acceptance และผู้มีสิทธิ์เป็นคน deploy ตาม policy

สิทธิ์ควรสอดคล้องกับหน้าที่ และ secrets ควรเก็บนอก source control ในช่องทางที่องค์กรอนุมัติ

ถ้าติด network หรือ policy บนเครื่องบริษัท ให้เก็บ error, เวลา และขั้นตอนที่ทำ แล้วส่งต่อทีม IT หรือ Security ที่รับผิดชอบครับ

07 / 08 · ประมาณ 1.5 นาที

ใช้ guardrails ตาม risk ของ change

แนวทางไม่จำเป็นต้องมีขั้นตอนหนักเท่ากันทุก change ครับ การแก้ข้อความเล็ก ๆ อาจมี PR, reviewer และ checks พื้นฐานเพียงพอ

ส่วนการเปลี่ยน data flow, permission หรือ infrastructure มี impact มากขึ้น ก็อาจต้องเพิ่ม security review, UAT, approval และแผน rollback

ขนาดของ checks ควรสัมพันธ์กับ impact, data sensitivity, ความสามารถในการย้อนกลับ และจำนวนผู้ใช้ที่ได้รับผล นโยบายจริงให้ owner และผู้ดูแลระบบกำหนดครับ

08 / 08 · ปิดสั้น ๆ

3 ส่วนที่ทำงานร่วมกัน

สรุปครับ Branch กับ PR ช่วยให้ทีมตรวจ code change, environments ช่วยแยก purpose และ runtime, ส่วน pipeline กับ owners ช่วยควบคุม release และติดตามผล

ขนาดของ guardrails ควรสัมพันธ์กับ risk และ policy ของระบบ ขอบคุณครับ

หลังจบ · เตรียมตอบคำถาม

คำตอบสั้นที่ใช้ได้

Merge main แล้วขึ้น PROD เลยไหม?

ขึ้นกับ trigger ของ pipeline และ release policy ของทีม ยังสรุปจากชื่อ branch อย่างเดียวไม่ได้

Test ผ่านแล้วทำไมต้อง UAT?

Automated test ตรวจกรณีที่เขียนไว้ UAT ให้ owner ยืนยันว่าตรงความต้องการจริง

ต้องมีครบสาม environment ทุกงานไหม?

เลือกระดับการแยกตาม risk, cost, data และภาระดูแลครับ

ถ้าไม่มีสิทธิ์ deploy ช่วยอะไรได้?

เตรียม PR, test evidence, release notes และขั้นตอนตรวจหลัง deploy แล้วส่งต่อผู้มีสิทธิ์
