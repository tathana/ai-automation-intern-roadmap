00 · ตั้งภาพในหัว

หนึ่งตัวอย่างตลอดทั้งเรื่อง

สมมติทีมทำเว็บภายในสำหรับให้พนักงานส่งคำขอ วันนี้ต้องเพิ่มช่อง “ประเภทคำขอ” การแก้โค้ดเสร็จยังไม่ทำให้ผู้ใช้ได้ใช้งาน เราต้องรวมงาน ตรวจสอบ ทดลองกับผู้ใช้ที่เกี่ยวข้อง ปล่อยรุ่น และดูผลหลังปล่อย

แก้โค้ด→ตรวจ→ทดลอง→ปล่อย→ติดตาม
ใจความ: Branch ช่วยจัดการ “โค้ดของใครและเวอร์ชันไหน” ส่วน environment ช่วยจัดการ “โค้ดรุ่นนั้นรันที่ไหนและใครกำลังใช้”

01 · แนวคิด

DevOps คืออะไร

Development คือการสร้างและแก้ซอฟต์แวร์ Operations คือการทำให้ระบบใช้งานได้ ดูแลให้บริการต่อเนื่อง และตอบสนองเมื่อเกิดปัญหา DevOps เป็นแนวทางให้คนและขั้นตอนเหล่านี้เชื่อมกันตั้งแต่เริ่มงานถึงหลังปล่อย ไม่ใช่ชื่อเครื่องมือชิ้นหนึ่ง

ในการทำงานจริง DevOps ปรากฏเป็นการตกลงว่าใครตรวจงาน ทดสอบอะไร เก็บประวัติอย่างไร ใครปล่อยรุ่น ใครดูอาการหลังปล่อย และจะกู้บริการอย่างไรถ้าเกิดปัญหา เครื่องมืออย่าง Bitbucket, pipeline และ AWS ช่วยให้ขั้นตอนทำซ้ำและตรวจย้อนหลังได้

CI / CD พอที่ต้องรู้

คำหมายถึงตัวอย่าง
CI · Continuous Integrationรวมงานบ่อยและตรวจการเปลี่ยนแปลงเปิด PR แล้ว pipeline รันทดสอบ
Continuous Deliveryเตรียมรุ่นให้พร้อมปล่อย อาจรออนุมัติผ่าน test แล้วผู้มีสิทธิ์กด deploy
Continuous Deploymentปล่อยอัตโนมัติหลังผ่านเงื่อนไขรุ่นที่ผ่านทุก gate ถูกปล่อยเอง

Build คือเตรียมโค้ดให้รันได้, test คือเช็กพฤติกรรม, deploy คือนำรุ่นไปติดตั้งใน environment, release คือทำให้ผู้ใช้เข้าถึงความสามารถนั้น บางระบบ deploy และ release พร้อมกัน บางระบบแยกกัน

Pipeline ที่ผ่านไม่ได้รับประกันว่าธุรกิจพอใจหรือระบบปลอดปัญหา จึงยังต้องมีเกณฑ์ตรวจรับและการติดตามหลังปล่อยตามความเสี่ยงของงาน

02 · พื้นที่ใช้งาน

Environment: DEV, UAT, PROD

Environment คือชุดพื้นที่และค่าตั้งที่ทำให้แอปรันได้ เช่น แอป ฐานข้อมูล URL บัญชีบริการ และสิทธิ์ แต่ละพื้นที่มีผู้ใช้และวัตถุประสงค์ต่างกัน ชื่ออาจต่างกันตามองค์กร

พื้นที่ใครใช้ / ใช้ทำอะไรข้อมูลและข้อควรระวัง
Local / DEVนักพัฒนาลองแก้และทดสอบเร็วใช้ข้อมูลจำลองหรือข้อมูลที่อนุญาต ความเปลี่ยนแปลงเกิดบ่อย
UAT · User Acceptance Testingผู้ใช้หรือเจ้าของงานตรวจว่าตรงโจทย์ควรใกล้เคียงการใช้งานจริงพอให้ตรวจความต้องการได้
PROD · Productionผู้ใช้จริงใช้งานสิทธิ์และการเปลี่ยนแปลงต้องควบคุมตามผลกระทบ

สมมติเพิ่มช่องประเภทคำขอ: ใน DEV นักพัฒนาลองบันทึกข้อมูล; ใน UAT เจ้าของงานตรวจว่าชื่อประเภทและขั้นอนุมัติตรงกระบวนการ; ใน PROD ผู้ใช้จริงเริ่มส่งคำขอ

แยก environment แล้วต้องระวังอะไร

  • Configuration เช่น URL หรือชื่อฐานข้อมูล ต้องชี้ไปยังปลายทางของ environment นั้น
  • Secret เช่น token, key, password ต้องเก็บในระบบที่องค์กรอนุญาตและจำกัดสิทธิ์ ไม่ใส่ไว้ใน Git
  • UAT ควรคล้าย PROD ในจุดที่มีผลต่อการทดสอบ แต่ข้อมูลลูกค้าจริงต้องใช้ตามนโยบายองค์กร
  • การแยกพื้นที่มีค่าใช้จ่ายและภาระดูแล จึงเลือกระดับการแยกให้สัมพันธ์กับความเสี่ยง
จุดที่มักสับสน: Branch ใน Git กับ environment บนเครื่องหรือ cloud เป็นคนละอย่าง การมี branch ชื่อ uat ไม่ได้แปลว่ามี UAT ที่รันได้จริง และโค้ดเดียวกันอาจถูก deploy ไปหลาย environment ด้วย config ต่างกัน

03 · จัดการการเปลี่ยนแปลง

Branching strategy ที่อธิบายได้ใน 15 นาที

Git เก็บประวัติการแก้ไฟล์ Branch คือเส้นทางทำงานที่แยกจากเส้นหลักชั่วคราว ส่วน Bitbucket เป็นที่เก็บ repository และเปิด Pull Request (PR) เพื่อให้ทีมตรวจงานก่อนรวมการเปลี่ยนแปลง

main→feature branch→PR + review→merge เข้า main

ตัวอย่าง: สร้าง feature/request-type เพื่อเพิ่มช่องประเภทคำขอ เมื่อแก้เสร็จเปิด PR อธิบายสิ่งที่เปลี่ยน วิธีตรวจ และผลกระทบ Reviewer อ่านโค้ดและผลทดสอบ แล้วจึง merge ตามสิทธิ์ที่ทีมกำหนด

ทำไม PR มีประโยชน์

  • คนอื่นมองเห็นเหตุผลและผลของการเปลี่ยนแปลง
  • ตรวจข้อผิดพลาดและถามสิ่งที่ไม่ชัดก่อนรวมงาน
  • เชื่อมผล pipeline กับการอนุมัติ และตามประวัติกลับได้

Branch protection คือกติกาที่ตั้งกับ branch สำคัญ เช่น ไม่ให้ push ตรง ต้องมี reviewer หรือผ่าน pipeline ก่อน merge การตั้งค่าจริงขึ้นกับสิทธิ์และนโยบายของทีม

อย่าจำสูตรว่า “merge เข้า main = ขึ้น production” เสมอไป การ merge, deploy ไป UAT, อนุมัติ และปล่อย production เป็นเหตุการณ์ที่อาจแยกกัน

เลือก strategy อย่างไร

สำหรับการอธิบายครั้งนี้ ใช้ main ที่ดูแลให้เสถียร + feature branch ที่อายุสั้น + PR เป็นตัวอย่างพื้นฐาน หากทีมมี release branch, hotfix branch หรือกฎ Bitbucket อยู่แล้ว ต้องยึดกฎนั้น การมี branch มากขึ้นเพิ่มภาระ merge จึงควรมีเหตุผลจากวิธีปล่อยงานจริง

04 · ประกอบเข้าด้วยกัน

เส้นทางหนึ่งของการส่งงาน

  1. รับโจทย์และระบุเกณฑ์ยอมรับ: ช่องประเภทคำขอต้องบันทึกและแสดงตรงไหน
  2. สร้าง feature branch แล้วแก้โค้ด ทดสอบบน local/DEV
  3. เปิด PR ใน Bitbucket ให้ reviewer ตรวจ และให้ CI ตรวจสิ่งที่ทำอัตโนมัติได้
  4. Merge ตามกติกาทีม แล้ว deploy รุ่นที่ระบุชัดไป UAT
  5. เจ้าของงานตรวจรับ ถ้าผ่านจึงขออนุมัติ release ไป PROD ตามสิทธิ์ขององค์กร
  6. หลังปล่อย ตรวจสัญญาณที่ตกลงไว้ เช่น error, งานค้าง และ feedback

Rollback หมายถึงกลับไปใช้รุ่นหรือสถานะก่อนหน้าเมื่อรุ่นใหม่มีปัญหา แต่การย้อนแอปอาจไม่ย้อนข้อมูลที่เปลี่ยนในฐานข้อมูล จึงต้องมีแผนสำหรับ migration และข้อมูลด้วยตามลักษณะระบบ

นี่เป็นตัวอย่าง workflow เพื่ออธิบายแนวคิด ไม่ใช่คำบรรยายว่าองค์กรใช้ขั้นตอนนี้อยู่แล้ว

05 · นำไปคุยกับทีม

บริบท Bitbucket, AWS และเครื่ององค์กร

เมื่อทีมใช้ Bitbucket เราพูดถึง branch, PR และ review บนแพลตฟอร์มที่ทีมรู้จักได้ ส่วนการ deploy ไป AWS ต้องทราบก่อนว่าใครเป็นเจ้าของ account, environment, pipeline และสิทธิ์อนุมัติ นักศึกษาฝึกงานอาจมีหน้าที่เตรียมโค้ด หลักฐานทดสอบ และเอกสาร โดยการปล่อยจริงอยู่กับผู้มีสิทธิ์

Zscaler หรือข้อจำกัดเครือข่ายบนเครื่องบริษัทอาจทำให้เข้าถึงบางบริการหรือรันเครื่องมือไม่เหมือนเครื่องส่วนตัว หากติดปัญหา ให้เก็บข้อความ error เวลา และขั้นตอนที่ทำ แล้วส่งให้ช่องทาง IT/ผู้ดูแลที่บริษัทกำหนด ข้อมูลที่มีอยู่ยังไม่พอระบุสาเหตุของปัญหาใดปัญหาหนึ่ง

คำถามที่ควรชวนทีมตอบ

  • งานประเภทใดต้องมี UAT และใครเป็นผู้ตรวจรับ?
  • ใคร review PR, ใคร merge, ใครอนุมัติและทำ production deployment?
  • แต่ละ environment ใช้ข้อมูลและ secrets อย่างไร?
  • ถ้าปล่อยแล้วมีปัญหา ใครตัดสินใจ rollback และมีวิธีตรวจผลอย่างไร?
  • เมื่อสิทธิ์หรือเครือข่ายขัดขวางการทำงาน ควรประสานใครพร้อมหลักฐานอะไร?

06 · เตรียมตอบ

คำถามที่อาจเจอ

ทุกระบบต้องมี DEV / UAT / PROD ครบไหม?

ไม่จำเป็นเสมอ จำนวนและรูปแบบขึ้นกับผลกระทบ ค่าใช้จ่าย นโยบาย และวิธีตรวจรับ แต่ต้องรู้ว่าทดสอบที่ไหน ใครตรวจ และการเปลี่ยนแปลงไปถึงผู้ใช้จริงอย่างไร

มี feature branch แล้ว ยังต้องมี DEV/UAT ไหม?

Branch แยกประวัติโค้ด ส่วน environment เป็นพื้นที่ที่ระบบรัน จึงช่วยคนละเรื่อง

CI ผ่านแล้ว ปล่อย PROD ได้เลยไหม?

ขึ้นกับเกณฑ์และสิทธิ์ของระบบนั้น CI ตรวจสิ่งที่ตั้งไว้ เช่น build/test แต่การยอมรับจากเจ้าของงานและการอนุมัติอาจยังจำเป็น

ถ้าไม่มีสิทธิ์ AWS เราช่วยอะไรได้?

เตรียม PR, test evidence, config requirements, release notes และขั้นตอนตรวจหลัง deploy แล้วประสานผู้มีสิทธิ์ตาม workflow ของบริษัท

ควรใช้ Git Flow หรือ trunk-based development?

ไม่มีคำตอบเดียวสำหรับทุกทีม ครั้งนี้เสนอ main + feature branch อายุสั้น + PR เป็นแบบจำลองที่อธิบายง่าย การเลือกจริงต้องดูรอบ release, จำนวนผู้ร่วมงาน และกติกาที่ใช้อยู่

ถ้าถูกถามรายละเอียดระบบจริงที่เราไม่รู้?

ตอบขอบเขตตรง ๆ: “ส่วนนี้ผมยังไม่มีข้อมูลยืนยันของระบบเรา หลักทั่วไปคือ… หากจะใช้จริงควรตรวจกับเจ้าของระบบ/ผู้ดูแลสิทธิ์ก่อน”

แนวพูดเปิด: “วันนี้ผมจะใช้ตัวอย่างสมมติหนึ่งระบบ เพื่อเชื่อม DevOps, environment และ branching ให้เห็นเป็นเส้นทางเดียว แล้วชวนคุยว่าขั้นตอนไหนเหมาะกับงานของทีมเรา”
