01 · เหตุผลของกระบวนการ

DevOps ลดความเสี่ยงตรงไหน

การเปลี่ยนระบบหนึ่งครั้งมีความเสี่ยงอย่างน้อยสี่ด้าน: โค้ดผิด, ความต้องการธุรกิจไม่ตรง, environment ต่างกัน และปล่อยแล้วไม่มีใครเห็นปัญหา แต่ละขั้นของ workflow ลดความเสี่ยงคนละชนิด

ขั้นช่วยจับอะไรยังจับอะไรไม่ได้ทั้งหมด
Code reviewเหตุผลของโค้ด ข้อผิดพลาดที่คนเห็นพฤติกรรมทุกกรณีเมื่อรันจริง
Automated testกรณีที่เขียนทดสอบไว้ข้อกำหนดที่ลืมหรือไม่ได้เขียนทดสอบ
UATความตรงกับวิธีทำงานของผู้ใช้โหลดจริงและปัญหาที่เกิดเฉพาะ production
Monitoring หลังปล่อยความผิดปกติในระบบจริงปัญหาที่ไม่มีสัญญาณหรือไม่มีคนตรวจ

ดังนั้นคำว่า “pipeline ผ่าน” แปลว่าเงื่อนไขที่ตั้งไว้ผ่าน ไม่ได้แปลว่าไม่มีความเสี่ยงเหลือเลย

02 · DEV / UAT / PROD

แยก environment ให้มีความหมาย

การแยก environment ไม่ใช่แค่ตั้งชื่อสามชุด สิ่งที่ควรถามคือรันแอปคนละที่หรือไม่, ใช้ฐานข้อมูลใด, ใครเข้าถึงได้, ค่าตั้งและ secret มาจากไหน และข้อมูลใน UAT เหมาะกับการตรวจรับหรือไม่

มิติคำถามที่ใช้ตรวจ
Isolationการทดลองใน DEV กระทบข้อมูลและผู้ใช้ PROD ได้หรือไม่?
ParityUAT คล้าย PROD พอที่จะตรวจพฤติกรรมสำคัญหรือไม่?
Dataใช้ข้อมูลจำลองหรือข้อมูลที่ได้รับอนุญาต? มีข้อมูลส่วนบุคคลหรือไม่?
Accessใคร deploy, ใครอ่าน log, ใครเปลี่ยน secret ได้?
Costทรัพยากรที่เปิดเพิ่มมีค่าใช้จ่ายและคนดูแลเพียงพอหรือไม่?

Environment parity คือความใกล้เคียงระหว่างพื้นที่ทดสอบกับพื้นที่จริงในส่วนที่สำคัญ ไม่จำเป็นต้องเหมือนกันทุกขนาด หาก UAT ใช้ฐานข้อมูลจำลองขนาดเล็ก ก็อาจตรวจ workflow ได้ แต่ไม่พิสูจน์สมรรถนะเมื่อมีข้อมูลมาก

Configuration drift คือการที่ค่าตั้งของพื้นที่ต่าง ๆ ค่อย ๆ ต่างกันโดยไม่มีใครรู้ เช่นเปิด feature หรือเปลี่ยน endpoint เฉพาะที่หนึ่ง ทำให้ “ผ่าน UAT แต่พังใน PROD” ได้ การเก็บค่าตั้งแบบตรวจย้อนหลังได้และเปรียบเทียบก่อนปล่อยช่วยลดปัญหานี้

อย่านำข้อมูลจริงเข้า DEV/UAT เพียงเพื่อให้เหมือน PROD ต้องดูนโยบายข้อมูลและวิธีทำข้อมูลจำลองหรือปกปิดข้อมูลก่อน

03 · Git strategy

Branching strategy คือการเลือกระยะเวลาที่งานแยกจากกัน

การแยก feature branch ช่วยให้คนทำงานไม่รบกวน branch หลัก แต่ถ้า branch อยู่ยาวและไม่อัปเดตจากงานทีม การรวมกลับมาจะยากขึ้น นี่เป็นเหตุผลที่คำว่า “feature branch อายุสั้น” สำคัญพอ ๆ กับการมี PR

แนวทางเหมาะเมื่อภาระที่ต้องรับ
Main + short feature branch + PRทีมรวมงานบ่อยและต้องการ review ชัดเจนต้องแบ่งงานเล็กและไม่ปล่อย branch ค้างนาน
Release branchต้องดูแลรุ่นที่จะปล่อยพร้อมพัฒนารุ่นถัดไปต้องตามว่า fix อยู่ branch ไหนและส่งกลับอย่างไร
Trunk-based developmentทีมรวมงานเข้าเส้นหลักถี่มากและมีการตรวจอัตโนมัติพร้อมต้องรักษา main ให้พร้อมใช้ด้วยงานชิ้นเล็กหรือ feature flags

ไม่ต้องยกทุก model บนสไลด์ หลักที่เสนอคือ branch สั้น → PR มีคำอธิบาย → review และ test → merge ส่วนกฎจริงใน Bitbucket ต้องดูของทีม เช่น required reviewers และ merge checks

Branch ไม่ได้แทน environment

Branch คือชุดการเปลี่ยนแปลงใน Git ส่วน environment คือระบบที่รันจริง ทีมอาจ deploy commit เดียวกันไป UAT ก่อน แล้วนำ artifact รุ่นเดียวกันไป PROD เพื่อให้มั่นใจว่ารุ่นที่ตรวจแล้วคือรุ่นที่ปล่อย หาก build ใหม่คนละครั้ง ควรมีวิธียืนยันว่าได้ผลเทียบเท่ากัน

04 · Release engineering

จาก merge ไปถึง release ยังมีการตัดสินใจ

Commit คือจุดในประวัติ Git; artifact คือผล build ที่พร้อม deploy เช่น container image; deployment คือการติดตั้ง artifact ใน environment; release คือผู้ใช้ได้รับความสามารถใหม่ ขั้นเหล่านี้อาจเกิดคนละเวลา

commit→build + test→artifact→UAT→approval→PROD

Approval gate คือจุดที่ต้องมีคนหรือระบบอนุมัติก่อนก้าวต่อ เช่น เจ้าของงานยืนยัน UAT หรือผู้ดูแลระบบอนุมัติ production deployment จุดนี้ควรมีหลักฐานว่าทดสอบอะไร ผ่านเกณฑ์ใด และจะตรวจหลังปล่อยอย่างไร

Rollback ควรคิดก่อนปล่อย

วิธีง่ายสุดอาจเป็นการนำ artifact รุ่นก่อนกลับมารัน แต่ถ้ารุ่นใหม่เปลี่ยน schema หรือเขียนข้อมูลรูปแบบใหม่ การย้อนแอปอาจทำงานกับข้อมูลใหม่ไม่ได้ จึงต้องคิดเรื่อง database migration, compatibility และ backup/restore ตามความเสี่ยงของระบบ

Roll forward คือแก้ปัญหาด้วยรุ่นใหม่แทนการย้อนกลับ บางเหตุการณ์ทำแบบนี้ได้เร็วกว่า ทางเลือกจริงขึ้นกับอาการ ผลกระทบ และผู้มีอำนาจตัดสินใจ

สำหรับคำพูด 15 นาที ให้พูดเพียงว่า “หลังปล่อยต้องตรวจผลและมีแผนกลับหรือแก้ต่อ โดยฐานข้อมูลอาจทำให้ rollback ซับซ้อนกว่าการย้อนโค้ด”

05 · ข้อจำกัดในองค์กร

ทีมที่ไม่มีสิทธิ์ deploy เองมีส่วนร่วมอย่างไร

สิทธิ์ควรสอดคล้องกับหน้าที่ คนเขียนโค้ดอาจเปิด PR และเตรียมผลทดสอบได้ แต่การเปลี่ยนทรัพยากร AWS หรือปล่อย production อาจเป็นหน้าที่ของผู้ดูแลที่ได้รับสิทธิ์ นี่ไม่ใช่อุปสรรคต่อ DevOps หากขั้นส่งต่อชัดและมีหลักฐานครบ

  • เตรียม PR ที่อธิบายการเปลี่ยนแปลงและวิธีทดสอบ
  • ระบุ config/secret ที่ระบบต้องใช้ โดยไม่ส่งค่า secret ใน repo หรือข้อความทั่วไป
  • บอกวิธีตรวจ UAT และผลที่คาดว่าจะเห็น
  • เตรียม release note, จุดเฝ้าดูหลังปล่อย และแนวทางรับมือหากพบปัญหา

หาก Bitbucket, AWS หรือเครื่องบริษัทถูกควบคุมด้วยนโยบายเครือข่าย ให้บันทึก error ที่เห็น เวลา URL หรือขั้นตอนที่เกี่ยวข้องในระดับที่แชร์ได้ แล้วส่งผ่านช่องทาง IT ที่กำหนด การเห็น Zscaler ในเครื่องยังไม่พิสูจน์ว่า Zscaler เป็นสาเหตุของทุกปัญหา

06 · ศัพท์ที่อาจถูกถาม

คำสั้น ๆ พร้อมความหมาย

ศัพท์ความหมายแบบพูดได้
Pipelineลำดับขั้นที่รันซ้ำได้ เช่น build → test → deploy
Artifactผล build รุ่นหนึ่งที่พร้อมนำไปรัน
Gateเงื่อนไขหรือการอนุมัติก่อนผ่านขั้นต่อไป
Secretข้อมูลลับที่ใช้ยืนยันสิทธิ์ เช่น token
Branch protectionกฎป้องกันการเปลี่ยน branch สำคัญโดยไม่ผ่านเงื่อนไข
Observabilityการดูสัญญาณ เช่น log, metric, trace เพื่อเข้าใจอาการระบบ
Infrastructure as Codeจัดการทรัพยากรระบบด้วยไฟล์ที่ตรวจและตามประวัติได้

ศัพท์เหล่านี้ช่วยตอบคำถาม ไม่จำเป็นต้องยัดทั้งหมดลงในเวลา 15 นาที

เนื้อหาเป็นกรอบคิดทั่วไป ไม่ยืนยัน architecture, policy หรือสิทธิ์ของบริษัท · เปิดสคริปต์พูด
