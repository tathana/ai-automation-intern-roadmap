ออกแบบ Data Pipeline

จำแค่นี้

1. Extract2. Validate3. แยกแถวผิด4. Transform5. Reconcile6. Load

ทฤษฎีที่ใช้ทำงาน

ขั้นตอนและ run_id

Extract, validate, transform, load เป็นแนวคิดพื้นฐาน ลำดับจริงขึ้นกับระบบ แยกขั้นให้รู้ว่าพังตรงไหน ใช้ run_id เชื่อมเหตุการณ์ในรอบเดียวกัน

Schema และ grain

ระบุชนิด ฟิลด์บังคับ ค่าอนุญาต เขตเวลา หน่วยเงิน และความหมายหนึ่งแถว เช่น request_id เป็นข้อความ ส่วน submitted_at ต้องตีความเวลาตรงกัน

Null ไม่ใช่ศูนย์

0 คือค่าจริง null คือไม่ทราบ อย่าแทนข้อมูลขาดด้วยศูนย์โดยไม่มีข้อตกลง เพราะผลอาจดูครบทั้งที่ข้อมูลหาย

ซ้ำหรือประวัติหลายเหตุการณ์

หลายแถวที่มี request_id เดียวกันอาจเป็น status events ต้องตกลงว่าจะเก็บทั้งหมดหรือเลือกสถานะล่าสุดด้วยเวลาและกฎเมื่อเวลาเท่ากัน ไม่ลบซ้ำทันที

ข้อมูลผิดและมาช้า

แยก rejected rows พร้อมเหตุผล เกณฑ์หยุดหรือทำต่อให้ตกลงกับเจ้าของงาน ข้อมูลมาช้าต้องมีวิธี backfill โดยไม่สร้างผลซ้ำ

Reconciliation

ตรวจแถวเข้า=ผ่าน+ปฏิเสธ ถ้ามี dedup ให้แยกจำนวนตัดออก เก็บที่มา ช่วงเวลาและเวอร์ชันการแปลงในพื้นที่ที่อนุญาต Join อาจทำให้แถวเพิ่ม ต้องตรวจ cardinality

ก่อน–หลัง: ทำโจทย์ให้ตรวจได้

ยังคลุมเครือ

ลบ null และ duplicate ให้หมด

ชัดขึ้น

กำหนดความหมายข้อมูลก่อน แยกแถวผิดและกติกาซ้ำ เก็บ null ตามจริง แล้วตรวจจำนวนก่อนคำนวณ

ตัวอย่าง: แถวเข้า 4 แถว แต่ใช้คำนวณ 2 รายการ

ข้อตกลงจำลอง: หนึ่งแถวแทนรายการ ยอดต้องมีค่า แถวที่เหมือนกันทุกฟิลด์ถือว่าซ้ำและเก็บหนึ่งแถว

id,amount,status
R01,80,completed
R01,80,completed
R02,20,pending
R03,,completed

ผลตรวจ: ผ่าน 2 รายการ (R01, R02) / ซ้ำ 1 แถว / ปฏิเสธ 1 แถวเพราะยอดขาด รวม 2 + 1 + 1 = 4 แถวเข้า ถ้า id เดียวกันแต่ค่าต่างกันต้องใช้กติกาความขัดแย้ง ไม่ตัดทิ้งเอง

ทำความเข้าใจให้ลึกขึ้น

Grain เป็นตัวกำหนดว่าควรนับอะไร

Grain คือหนึ่งแถวแทนสิ่งใด ถ้าแทนหนึ่งคำขอ count rows อาจนับคำขอได้ แต่ถ้าแทนหนึ่งการเปลี่ยนสถานะ คำขอเดียวอาจมีห้าแถว การนับแถวจะกลายเป็นจำนวนเหตุการณ์

นึกภาพตาม: ก่อน dedup ถามว่าเหตุการณ์เก่าจำเป็นต่อการวิเคราะห์หรือไม่ การทิ้งประวัติอาจทำให้คำนวณระยะเวลารอไม่ได้

Quarantine ต่างจากลบทิ้ง

Quarantine คือแยกข้อมูลที่ยังใช้ไม่ได้พร้อมเหตุผล เพื่อให้คนตรวจหรือแก้ภายหลัง คุณยังตรวจได้ว่าแถวหายไปไหน ต้องเลือกพื้นที่เก็บและระยะเวลาเก็บตามบริษัท ไม่ใส่ข้อมูลอ่อนไหวทั้งหมดลง log

นึกภาพตาม: ถ้าจำนวนเงินเป็น “ไม่ทราบ” ให้แยก rejected พร้อมเหตุผล แทนเปลี่ยนเป็น 0 แล้วปล่อยให้ยอดรวมดูถูกต้อง

Backfill ต้องคิดเรื่องผลซ้ำ

Backfill คือประมวลผลข้อมูลช่วงเก่าที่มาช้าหรือเคยพลาด ต้องกำหนดช่วงและเวอร์ชันข้อมูล รวมถึงวิธีแทนที่หรือปรับผลเดิม ไม่เพิ่มยอดเก่าซ้ำทุกครั้งที่รัน

นึกภาพตาม: รายงานวันที่ 14 ที่คำนวณใหม่วันที่ 16 ควรระบุว่าเป็นข้อมูลปรับปรุง ไม่ควรส่งเหมือนเป็นรอบใหม่โดยไม่ตรวจผู้รับและกติกาส่ง

Prompt พร้อมปรับใช้

เติม [วงเล็บ] ด้วยบริบทที่อนุญาต เลือกใช้ภาษาไทยหรืออังกฤษตามทีม

Prompt ภาษาไทย

ออกแบบ pipeline จาก [ข้อมูลจำลองและ schema]
ระบุ grain ชนิดข้อมูล ฟิลด์บังคับ เขตเวลา และหน่วยเงิน
แยก missing, zero, invalid และ duplicate
เสนอวิธีจัดการแถวผิดและข้อมูลมาช้า พร้อมเรื่องที่ต้องยืนยัน
แสดง input → accepted/rejected → output
กำหนด run_id และการตรวจจำนวนแถวก่อนหลังแต่ละขั้น
ยังไม่ลบหรือแก้ข้อมูลต้นทาง

Prompt English

Design a pipeline for [synthetic data and schema].
Define grain, types, required fields, timezone, and currency units.
Distinguish missing, zero, invalid, and duplicate values.
Propose rejected/late-data handling and flag decisions to confirm.
Show input -> accepted/rejected -> output.
Include run IDs and row-count reconciliation.
Do not modify or delete source data.

ทำไม Prompt นี้แบ่งแบบนี้

การระบุ grain ทำให้เลือกการนับและ dedup ได้ตรง schema กำหนดค่าที่รับได้ accepted/rejected ทำให้ตรวจข้อมูลที่หายไป ส่วน run_id และ reconciliation ช่วยติดตามทั้งรอบ

ปรับ [วงเล็บ] ก่อนใช้ และตัดข้อที่ไม่เกี่ยวข้องออก หากเป็นขั้นที่ทีมอนุมัติให้ดำเนินการแล้ว ให้ระบุขอบเขตที่อนุมัติแทนการหยุดรอซ้ำทุกครั้ง

เมื่อเจอปัญหา

ยอดเพิ่มหลัง join

สาเหตุที่เป็นไปได้: many-to-many คูณแถว

ตรวจต่อ: ตรวจ key และจำนวนก่อนหลัง

ยอดหาย

สาเหตุที่เป็นไปได้: ทิ้งข้อมูลผิดเงียบ ๆ

ตรวจต่อ: รายงานจำนวนและผลกระทบที่ตัดออก

ถามพี่อย่างไร

หนึ่งแถวแทนรายการหรือเหตุการณ์ และกติกาเลือกข้อมูลล่าสุดคืออะไรครับ

  • มีกฎ null และซ้ำ
  • มีรายการผิดแยก
  • กระทบยอดได้
