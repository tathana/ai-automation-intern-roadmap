ทำให้ Automation เชื่อถือได้

ไปที่ Prompt พร้อมใช้ ↓
จำแค่นี้

แต่ละขั้นพังได้ รันซ้ำแล้วต้องไม่เพิ่มผลเกินที่ตั้งใจ

1. พบ error2. จำแนก3. ตรวจผลเดิม4. Retry / หยุด5. แจ้งและกู้

ทฤษฎีที่ใช้ทำงาน

Transient / permanent

Timeout หรือบาง 5xx อาจชั่วคราว ส่วนข้อมูลผิดหรือสิทธิ์ไม่พอมักต้องแก้ต้นเหตุ 429 ให้ดูนโยบายบริการและ Retry-After เมื่อมี ไม่ retry ทุก error เท่ากัน

Retry มีขอบเขต

กำหนด timeout จำนวนครั้งและช่วงรอ เช่น backoff พร้อม jitter การรอ response ไม่สำเร็จไม่ได้แปลว่าปลายทางยังไม่ทำงาน จึงต้องตรวจผลข้างเคียงก่อนลองใหม่

Idempotency

ใช้ business key หรือ idempotency key ที่บริการรองรับและบันทึกสถานะอย่างเหมาะสม เช็กก่อนแล้วค่อยเขียนอาจแข่งกันเมื่อหลาย worker ต้องพิจารณา unique constraint หรือ transaction ตามเทคโนโลยี

Partial failure

บันทึกผลแล้วแต่ส่งรายงานล้มเหลว ควรกลับมาทำต่อขั้นที่เหมาะ ไม่ทำทุกขั้นซ้ำโดยไม่ตรวจ สถานะที่เก็บต้องสะท้อนสิ่งที่สำเร็จจริง

Log ที่ใช้แก้ปัญหา

เก็บ run_id ขั้นตอน เวลา สถานะ จำนวนข้อมูล และ error type โดยไม่บันทึก secrets หรือข้อมูลส่วนบุคคลเกินจำเป็น Python logging มีระดับและ handler ให้จัดตามทีม

Alert / runbook

มี log ไม่เท่ากับมีคนรู้ว่าพัง ระบุผู้รับแจ้งและขั้นตอนกู้คืน n8n มีแนวทาง error workflow แต่ต้องตรวจพฤติกรรมตามเวอร์ชันและการตั้งค่าจริง

อ่านรายละเอียดเฉพาะเครื่องมือ: Python: logging · n8n: Error handling

ก่อน–หลัง: ทำโจทย์ให้ตรวจได้

ยังคลุมเครือ

ถ้าผิดให้ลองจนผ่าน

ชัดขึ้น

แยก error กำหนด retry/timeout ตรวจผลเดิมและความปลอดภัยเมื่อซ้ำ แล้วแจ้งผู้ดูแลเมื่อหมดโอกาส

ทำความเข้าใจให้ลึกขึ้น

Timeout เป็นความไม่แน่ใจ

ผู้เรียกหยุดรอได้ทั้งตอนปลายทางยังไม่เริ่มและตอนปลายทางทำเสร็จแล้ว การส่งคำสั่งเดิมใหม่ทันทีจึงอาจสร้างรายการซ้ำ ต้องใช้วิธีตรวจผลหรือ key ที่ปลายทางรองรับ

นึกภาพตาม: สำหรับรายงานที่ส่งออกแล้วแต่ยังไม่ได้บันทึก receipt ควรมีขั้นตรวจสถานะก่อนส่งซ้ำ หากตรวจไม่ได้ให้ใช้กระบวนการคนช่วยตัดสินใจตามทีม

เหตุใดเช็กซ้ำอย่างเดียวไม่พอ

สอง worker อาจเช็กพร้อมกันว่าไม่มีรายการ แล้วทั้งคู่สร้างรายการใหม่ได้ นี่คือ race condition ต้องให้กลไกบันทึกบังคับความไม่ซ้ำ หรือใช้ transaction ตามระบบ ไม่พึ่ง if ในโค้ดอย่างเดียว

นึกภาพตาม: Unique constraint ป้องกันแถวซ้ำในฐานข้อมูลได้ แต่ไม่รับประกันว่าอีเมลหรือ API ภายนอกถูกเรียกครั้งเดียว ต้องออกแบบปลายทางร่วมกัน

สรุปสถานะให้คนแก้งานได้

คนรับ alert ควรรู้ว่ารอบไหน ขั้นไหน และผลส่วนไหนเกิดแล้ว พร้อมลิงก์ที่มีสิทธิ์ดู ไม่ส่ง error ดิบยาว ๆ อย่างเดียว กำหนดด้วยว่าใครตัดสินใจรันต่อหรือยกเลิก

นึกภาพตาม: ข้อความ “failed” ต่างจาก “อ่านข้อมูลครบแล้ว แต่ส่งรายงานไม่สำเร็จ ยังไม่ยืนยันผลที่ปลายทาง” ประโยคหลังช่วยเลือกวิธีกู้ได้ถูก

Prompt พร้อมปรับใช้

เติม [วงเล็บ] ด้วยบริบทที่อนุญาต เลือกใช้ภาษาไทยหรืออังกฤษตามทีม

Prompt ภาษาไทย

ตรวจ workflow [รายละเอียด]
แต่ละขั้นระบุ failure mode ผลที่อาจเกิดแล้ว retry policy และวิธีกู้
รวม timeout หลังปลายทางสำเร็จ และสองรอบรันพร้อมกัน
เสนอ idempotency key / state / constraint ตาม stack จริง
กำหนด log ที่ไม่เผยข้อมูลลับและผู้รับแจ้งเมื่อ retry หมด
ส่งตารางการตัดสินใจและเคสทดสอบ
ไม่อ้าง exactly-once โดยไม่มีหลักฐาน

Prompt English

Review [workflow] reliability.
For each step identify failures, possibly completed effects, retries, and recovery.
Include timeouts after remote success and concurrent runs.
Propose idempotency keys, state, or constraints for the actual stack.
Define non-sensitive logs and escalation after retries are exhausted.
Return a decision table and tests.
Do not claim exactly-once behavior without evidence.

ทำไม Prompt นี้แบ่งแบบนี้

กรณี timeout หลังสำเร็จและ concurrent runs เป็นจุดที่ retry ธรรมดาพลาดได้ ตารางตัดสินใจช่วยให้ผู้ตรวจเห็นว่า error แบบใดทำอะไรต่อ ส่วนไม่อ้าง exactly-once ช่วยให้ระบุขอบเขตที่พิสูจน์ได้

ปรับ [วงเล็บ] ก่อนใช้ และตัดข้อที่ไม่เกี่ยวข้องออก หากเป็นขั้นที่ทีมอนุมัติให้ดำเนินการแล้ว ให้ระบุขอบเขตที่อนุมัติแทนการหยุดรอซ้ำทุกครั้ง

เมื่อเจอปัญหา

อีเมลซ้ำ

สาเหตุที่เป็นไปได้: ส่งแล้ว timeout จึงส่งใหม่

ตรวจต่อ: ตรวจ receipt/key ถ้ายืนยันไม่ได้ให้ส่งตรวจ

พังเงียบ

สาเหตุที่เป็นไปได้: จับ exception แล้วถือว่าสำเร็จ

ตรวจต่อ: สะท้อน failed/incomplete และแจ้ง

ถามพี่อย่างไร

ถ้ารอบหนึ่งทำได้ครึ่งเดียวให้รันต่อจากไหน และใครรับแจ้งครับ

ก่อนข้ามไปขั้นต่อไป

  • จำแนก error
  • retry มีขอบเขต
  • ทดสอบซ้ำ/พร้อมกัน
  • มีเจ้าของและวิธีกู้
