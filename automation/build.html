CHAPTER 04 / 10

สั่ง AI สร้างระบบเป็นขั้นตอน

ไปที่ Prompt พร้อมใช้ ↓
จำแค่นี้

งานเล็กทำครบ งานใหญ่แบ่งตามผลลัพธ์ที่ตรวจได้

1. อ่าน2. วางแผน3. ทำส่วนเล็ก4. ตรวจ5. ขยาย

ทฤษฎีที่ใช้ทำงาน

ขนาดงานกับโครง prompt คนละเรื่อง

สั่งครั้งเดียวก็แบ่งหัวข้อได้ ฟังก์ชันเล็ก input/output ชัดทำจบได้ ส่วนระบบหลายขั้นตกลงแผนและส่วนเชื่อมต่อก่อน

เส้นทางเล็กที่ทำงานครบ

เริ่ม CSV จำลอง → validate → aggregate → HTML ก่อนต่อ API และส่งจริง จะตรวจนิยามข้อมูลได้ก่อนเจอปัญหาเครือข่าย

อ่านของเดิมก่อนแก้

ให้ไฟล์ที่เกี่ยวข้อง มาตรฐาน และพฤติกรรมที่ต้องรักษา ให้ AI สรุปสิ่งที่พบ อย่าสั่งสร้างโปรเจกต์ใหม่หากต้องต่อยอดระบบเดิม

ผลทดสอบจริง

แต่ละรอบส่งโค้ด วิธีรัน ผลทดสอบ และข้อจำกัด หาก AI ไม่มีเครื่องมือรัน ต้องระบุว่ายังไม่รัน ข้อความบอกว่าผ่านอย่างเดียวไม่ใช่หลักฐาน

แก้ต่อและส่งบริบท

บอก expected/actual, input ที่ทำให้ผิด และขอบเขตแก้ เมื่อเริ่มแชทใหม่ส่ง requirement ล่าสุด การตัดสินใจ ไฟล์ และปัญหาค้าง แทนประวัติทั้งหมด

ก่อน–หลัง: ทำโจทย์ให้ตรวจได้

ยังคลุมเครือ

สร้างทุกอย่างพร้อมขึ้น production

ชัดขึ้น

อ่านไฟล์ เสนอแผน แล้วทำ CSV ถึง HTML ด้วยข้อมูลจำลองให้ครบ พร้อมทดสอบ ก่อนต่อระบบจริง

ทำความเข้าใจให้ลึกขึ้น

แบ่งตามสิ่งที่ตรวจได้ ไม่ใช่แบ่งตามจำนวนไฟล์

หนึ่งรอบที่ดีควรเห็นพฤติกรรมที่ลองได้ เช่นอ่าน CSV แล้วแสดงจำนวนแถวผิด การแบ่งว่าเขียนไฟล์ A วันนี้ ไฟล์ B พรุ่งนี้อาจยังไม่มีอะไรให้ตรวจจนจบทุกไฟล์ จึงควรเริ่มจากเส้นทางเล็กที่ต่อกันครบ

นึกภาพตาม: ต้นแบบรายงานอาจเริ่มด้วยข้อมูลสามแถวและ HTML ง่าย ๆ ก่อน เมื่อสูตรถูกค่อยเพิ่ม API และรูปแบบรายงาน

กำหนดสัญญาระหว่างส่วน

บอกชื่อฟิลด์ ชนิดข้อมูล และกรณี error ของแต่ละขั้น เช่น validator ส่ง accepted และ rejected ส่วน aggregator รับเฉพาะ accepted หากไม่ตกลงไว้ AI อาจเขียนแต่ละส่วนด้วยรูปแบบคนละชุด

นึกภาพตาม: เมื่อเชื่อมไม่ได้ อย่าเพิ่งขอเขียนใหม่ทั้งระบบ ตรวจว่าชื่อคีย์และความหมาย output ของขั้นก่อนตรงกับ input ของขั้นถัดไปหรือไม่

ตรวจ AI ระหว่างทางอย่างไร

ขอให้สรุปไฟล์ที่เปลี่ยน เหตุผล วิธีรัน และผลทดสอบที่ทำจริง คุณอ่านส่วนที่มีผลต่อข้อมูล สูตร สิทธิ์ และการส่งออกเป็นพิเศษ ไม่จำเป็นต้องอนุมัติทุกบรรทัด แต่ต้องเข้าใจพฤติกรรมสำคัญก่อนส่งงานต่อ

นึกภาพตาม: ถ้าเครื่องมือแค่ส่งโค้ดในแชต ยังไม่มีหลักฐานว่าไฟล์ถูกสร้างหรือรันผ่าน ต้องนำไปตรวจในพื้นที่ที่ทีมอนุญาต

Prompt พร้อมปรับใช้

เติม [วงเล็บ] ด้วยบริบทที่อนุญาต เลือกใช้ภาษาไทยหรืออังกฤษตามทีม

Prompt ภาษาไทย

สร้างต้นแบบ [ระบบ] จาก [ไฟล์และ requirement]
เริ่มด้วยสรุปโจทย์ แผน และข้อมูลที่ขาด
หลังตกลงแผน ทำ CSV จำลอง → validate → aggregate → HTML
รักษามาตรฐานและ dependency เดิม
ไม่เรียก API จริง ส่งข้อความ หรือ deploy ในรอบนี้
ส่งไฟล์ที่แก้ วิธีรัน ผลทดสอบจริง และข้อจำกัด
ถ้ารันไม่ได้ ให้บอกชัดว่ายังไม่ได้ทดสอบ

Prompt English

Build [prototype] from [files and requirements].
First summarize the task, plan, and unknowns.
After agreement, implement synthetic CSV -> validate -> aggregate -> HTML.
Preserve existing conventions and dependencies.
No live API calls, messages, or deployment in this iteration.
Return changed files, run instructions, actual tests, and limitations.
Clearly identify any tests you could not execute.

ทำไม Prompt นี้แบ่งแบบนี้

เริ่มจากแผนเพื่อให้เห็นส่วนที่ขาด กำหนดเส้นทางเล็กเพื่อให้ตรวจได้เร็ว ข้อห้ามเชื่อมจริงจำกัดผลข้างเคียง ส่วนผลทดสอบจริงช่วยแยกงานที่เพียงเขียนออกจากงานที่รันแล้ว

ปรับ [วงเล็บ] ก่อนใช้ และตัดข้อที่ไม่เกี่ยวข้องออก หากเป็นขั้นที่ทีมอนุมัติให้ดำเนินการแล้ว ให้ระบุขอบเขตที่อนุมัติแทนการหยุดรอซ้ำทุกครั้ง

เมื่อเจอปัญหา

ส่วนต่าง ๆ ต่อไม่ได้

สาเหตุที่เป็นไปได้: schema คนละแบบ

ตรวจต่อ: ตกลง input/output และทดสอบเชื่อม

แก้แล้วของเดิมพัง

สาเหตุที่เป็นไปได้: ขอบเขตกว้างไม่มี regression

ตรวจต่อ: เพิ่มเคสที่ทำซ้ำปัญหาและตรวจของเดิม

ถามพี่อย่างไร

ทำข้อมูลจำลองให้เห็นผลครบก่อน แล้วส่งพี่ตรวจนิยามข้อมูลได้ไหมครับ

ก่อนข้ามไปขั้นต่อไป

  • มีขอบเขตรอบนี้
  • มีสัญญาส่วนเชื่อม
  • รู้สิ่งที่ยังไม่ทำ
  • แยกผลจริงกับข้อเสนอ
