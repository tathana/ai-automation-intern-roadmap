เชื่อม Workflow และระบบอื่น

จำแค่นี้

รู้ trigger สัญญาข้อมูล และผลข้างเคียงก่อนเชื่อมจริง

1. Trigger2. Auth3. Validate4. Process5. Approve6. Deliver

ทฤษฎีที่ใช้ทำงาน

เลือก trigger

Schedule ตามเวลา Webhook ตาม event และ manual เมื่อคนสั่ง เลือกตามความสดที่ต้องการ ระบุ timezone และกรณีรอบก่อนยังไม่จบ

อ่าน API contract

Endpoint, method, auth, request/response, pagination, rate limit และ errors ต้องมาจากเอกสารจริง ไม่ให้ AI เดารายละเอียด

สิทธิ์และ secrets

ใช้บัญชีและ secret store ที่อนุญาต ให้สิทธิ์เท่าที่จำเป็น ไม่ใส่ token ใน prompt หรือ log แชร์ error หลังตัดข้อมูลที่ไม่ควรเปิดเผย

ตอบรับไม่เท่ากับเสร็จ

Webhook บางระบบตอบรับแล้วเก็บงานเข้าคิว ต้องรู้ว่างานคงอยู่จริงและติดตามสถานะได้ การตอบ 200 ไม่ได้ยืนยันว่างานธุรกิจจบแล้ว

Dry-run ต้องไม่มีผลจริง

แยกเตรียม payload จากส่ง ทดสอบกับ sandbox หรือผู้รับทดสอบที่ตกลง คำว่า dry-run ใน prompt ไม่พอ โค้ดต้องไม่เรียกขั้นเขียนหรือส่งจริง

คนอนุมัติ

ใช้สถานะ pending/approved/rejected ตามกระบวนการ ระบุผู้อนุมัติ เวลารอ และผูกการอนุมัติกับเวอร์ชันข้อมูล หากข้อมูลเปลี่ยนต้องตรวจสิทธิ์ใหม่ตามกฎ

ก่อน–หลัง: ทำโจทย์ให้ตรวจได้

ยังคลุมเครือ

ต่อ API แล้วส่งเข้าแชตทีมทุกวัน

ชัดขึ้น

อ่าน docs ขอ sandbox ตรวจ pagination และแสดง payload ใน dry-run ก่อนเปิดส่งจริงพร้อมกันซ้ำ

ตัวอย่าง workflow รับคำขอและอนุมัติ

  1. รับ request_id และรายละเอียด → ตรวจ schema
  2. AI เสนอ category พร้อม evidence → โค้ดตรวจค่าอนุญาต
  3. สร้าง pending review สำหรับผู้มีสิทธิ์
  4. เมื่ออนุมัติ ให้บันทึกคน เวลา และเวอร์ชันข้อมูล
  5. ก่อนส่งต่อ ตรวจว่าข้อมูลยังเป็นเวอร์ชันที่อนุมัติ
  6. ดำเนินการด้วยบัญชีที่มีสิทธิ์และติดตาม receipt

ถ้าผู้ใช้แก้คำขอหลังอนุมัติ ต้องทำตามกติกาตรวจใหม่ของทีม โมเดลไม่มีสิทธิ์สร้างหลักฐานอนุมัติแทนคน

Prompt พร้อมปรับใช้

เติม [วงเล็บ] ด้วยบริบทที่อนุญาต เลือกใช้ภาษาไทยหรืออังกฤษตามทีม

Prompt ภาษาไทย

วางแผนเชื่อม [A] กับ [B] จาก API docs ที่ให้
สรุป trigger, auth, schema, pagination, timeout, rate limit ที่ระบุจริง
สิ่งที่ docs ไม่บอกให้เป็นคำถาม ห้ามเดา endpoint
รอบแรก dry-run แสดง payload จำลอง ไม่ส่งหรือแก้ข้อมูลจริง
ระบุผลข้างเคียง การกันซ้ำ และผู้อนุมัติก่อนเปิดใช้
ไม่ขอ secrets ผ่านแชต

Prompt English

Plan an integration between [A] and [B] using the supplied API docs.
Identify documented trigger, auth, schemas, pagination, timeouts, and rate limits.
List unknowns as questions; do not invent endpoints.
First build a dry-run showing synthetic payloads without live writes or sends.
Describe side effects, duplicate prevention, and activation approval.
Do not request secrets in chat.

เมื่อเจอปัญหา

ได้ข้อมูลแค่หน้าแรก

สาเหตุที่เป็นไปได้: ไม่มี pagination

ตรวจต่อ: ตรวจ cursor/จำนวนหน้าและยอด

ส่งจริงตอนทดสอบ

สาเหตุที่เป็นไปได้: config ปลายทางไม่แยก

ตรวจต่อ: ตรวจ allowlist ผู้รับและ sandbox

ถามพี่อย่างไร

มี sandbox และบัญชีทดสอบไหมครับ ขั้นส่งหรือแก้ข้อมูลจริงให้ใครอนุมัติครับ

ก่อนข้ามไปขั้นต่อไป

  • มี API contract
  • รองรับ pagination
  • dry-run ไม่ส่งจริง
  • รู้สิทธิ์และผู้อนุมัติ
