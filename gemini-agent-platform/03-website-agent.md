# บทที่ 3 — ปรับ Agent ให้สร้างและ Deploy เว็บไซต์

บทนี้เป็นการ **เปลี่ยน Agent เริ่มต้นจากบทก่อน ให้สร้างหน้าเว็บไซต์และนำขึ้น Firebase Hosting ได้จริง** โดยเพิ่มเครื่องมือสองตัวและปรับคำสั่งของ Agent

เนื้อหาด้านล่างเรียงตามเวลา อ้างอิงจากข้อความถอดเสียง ส่วนรายละเอียดที่ยังไม่ครบหรืออาจทำให้เข้าใจคลาดเคลื่อนจะระบุไว้ในจุดที่เกี่ยวข้อง

## เนื้อหาแบบละเอียด

### 0:00–1:26 — สาธิต Agent เวอร์ชันใหม่

หลังจากบทก่อนเตรียมสภาพแวดล้อมและรัน Agent ตัวแรกสำเร็จ ผู้บรรยายสร้าง **เวอร์ชันที่สอง** โดยปรับให้ทำงานเป็น Website Generator จริง

เริ่มสาธิตด้วยการเปิด Playground เปิด Streaming แล้วป้อนคำขอ มีใจความว่า:

> สร้าง Landing Page สำหรับบริษัทด้านการศึกษาและให้คำปรึกษา AI ชื่อ The AI Language ซึ่งพัฒนาระบบหลาย Agent โดยใช้ MCP, ADK, A2A และ Gemini Enterprise Agent Platform

Agent นี้มีเครื่องมือสองตัว:

1. **Save Website Content** — บันทึกโค้ดเว็บไซต์ที่สร้างขึ้น
2. **Deploy Saved Website** — นำเว็บไซต์ที่บันทึกแล้วขึ้น Firebase Hosting

ลำดับการทำงานในตัวอย่างคือ:

**รับคำขอ → สร้างโค้ดเว็บไซต์ → บันทึกไฟล์ในเครื่องที่รัน Agent → Deploy ขึ้น Firebase Hosting → ส่ง URL กลับ**

สิ่งที่เพิ่มจากบทก่อนจึงเป็นความสามารถในการดำเนินการกับบริการภายนอก จากเดิมที่มีเพียงเครื่องมือสภาพอากาศจำลอง

### 1:27–2:19 — ดูเว็บไซต์ที่สร้างสำเร็จ

ผู้บรรยายเปิด URL ที่ Agent ส่งกลับมา และแสดงหน้าเว็บไซต์บน Firebase Hosting องค์ประกอบที่กล่าวถึง ได้แก่:

- **Hero Section** — ส่วนเปิดหน้าเว็บที่สื่อสารข้อความหลัก
- **CTA หรือ Call to Action** — ปุ่มชวนให้ผู้เข้าชมดำเนินการ
- ส่วนแสดงเทคโนโลยีที่บริษัทใช้
- ส่วนที่เรียกว่า **Swarm Simulator**

ข้อความถอดเสียงไม่ได้อธิบายรายละเอียดการทำงานของ Simulator จึงยังสรุปไม่ได้ว่าเป็นการจำลองระบบ Agent จริงหรือเป็นองค์ประกอบสาธิตบนหน้าเว็บ

ผู้บรรยายเน้นว่า ผลลัพธ์นี้สร้างด้วย **Agent ตัวเดียว** แม้เนื้อหาบนเว็บไซต์จะพูดถึงระบบหลาย Agent ก็ตาม

เว็บไซต์ถูกนำขึ้น **Preview Channel** ของ Firebase Hosting ซึ่งเป็นช่องทางสำหรับดูตัวอย่างเว็บไซต์ก่อนนำไปใช้จริง

### 2:20–5:45 — สิ่งที่เปลี่ยนจากเวอร์ชัน 1 เป็นเวอร์ชัน 2

จุดเริ่มต้นคือ Agent ที่สร้างโครงด้วย CLI และตอบคำถามสภาพอากาศได้ จากนั้นปรับให้สร้างและ Deploy เว็บไซต์

| ส่วน | เวอร์ชันก่อน | เวอร์ชันใหม่ |
| --- | --- | --- |
| หน้าที่ | ผู้ช่วยเริ่มต้นและตัวอย่างสภาพอากาศ | สร้างเว็บไซต์ตามคำขอ |
| เครื่องมือ | ดูสภาพอากาศและเวลาปัจจุบัน | บันทึกเว็บไซต์และ Deploy เว็บไซต์ |
| การเชื่อมต่อ | ตัวอย่างเครื่องมือพื้นฐาน | Firebase Hosting ผ่าน CLI |
| Instructions | คำสั่งผู้ช่วยทั่วไป | คำสั่งสร้าง HTML และใช้เครื่องมือตามลำดับ |

**เครื่องมือแรก: บันทึกเนื้อหาเว็บไซต์**

Agent ส่งโค้ดที่สร้างขึ้นให้เครื่องมือบันทึกเป็นไฟล์ HTML ในโฟลเดอร์ชั่วคราวของเครื่องหรือเซิร์ฟเวอร์ที่รัน Agent โฟลเดอร์นี้ถูกออกแบบให้เครื่องมือทั้งสองเรียกใช้ร่วมกันได้

คำว่า “คงอยู่” ในบริบทนี้ควรเข้าใจว่า **ไฟล์ยังอยู่ให้การเรียกเครื่องมือถัดไปเข้าถึงได้ในสภาพแวดล้อมนั้น** ไม่ได้หมายความว่าเป็นพื้นที่เก็บถาวร หรือจะยังอยู่หลังรีสตาร์ตระบบเสมอไป

**เครื่องมือที่สอง: Deploy ไฟล์ที่บันทึกไว้**

เครื่องมือนี้เรียก **Firebase CLI** เพื่อนำไฟล์ขึ้น Hosting และส่งผลการ Deploy กลับให้ Agent

**เลือกใช้ Preview Channel**

ตัวอย่างใช้ช่องชื่อประมาณ `ai-generated-preview` แทนการ Deploy ทับช่องเว็บไซต์หลัก และตั้งอายุไว้ 30 นาทีตามที่ผู้บรรยายอธิบาย

เป้าหมายคือให้เว็บไซต์ทดสอบหมดอายุ ลดการทิ้งสภาพแวดล้อมทดลองค้างไว้ และช่วยควบคุมการใช้งานทรัพยากร

อย่างไรก็ตาม ข้อความไม่ได้แสดงคำสั่งจริง จึงต้องตรวจสอบว่า Firebase CLI เวอร์ชันที่ใช้อยู่รองรับรูปแบบและช่วงเวลาที่ระบุหรือไม่ อีกทั้ง **Preview URL ไม่ได้แปลว่าเป็นเว็บไซต์ส่วนตัวหรือมีระบบจำกัดผู้เข้าชมโดยอัตโนมัติ**

**การเลือก Google Cloud Project**

เครื่องมือพยายามอ่าน Project จากตัวแปรสภาพแวดล้อมก่อน หากไม่มีจึงอ่านค่าจากการตั้งค่า `gcloud`

ผู้บรรยายคาดหวังว่าจะมีตัวแปรดังกล่าวในสภาพแวดล้อม Serverless เช่น Cloud Run แต่เมื่อใช้งานจริงต้องตรวจสอบหรือตั้งค่าให้ชัดเจน ไม่ควรสมมติว่าจะมีอยู่เสมอ

**เรื่อง Node.js**

ผู้บรรยายกล่าวถึงการตั้งค่าบางอย่างเพื่อข้ามข้อกำหนดด้านเวอร์ชัน Node.js ในตัวอย่างการศึกษา แต่ข้อความไม่มีชื่อแฟล็กหรือค่าที่ใช้ จึงยังทำตามส่วนนี้จากข้อความอย่างเดียวไม่ได้ ทางเลือกที่ตรงไปตรงมาคือใช้ Node.js เวอร์ชันที่ Firebase CLI รองรับ

### 5:46–7:31 — เครื่องมือบันทึกเว็บไซต์ทำงานอย่างไร

ผู้บรรยายกลับมาที่ไฟล์ `app/agent.py` ซึ่งยังเป็นไฟล์หลักสำหรับนิยาม Agent การทำงานของเครื่องมือบันทึกเว็บไซต์มีลำดับดังนี้:

1. หาโฟลเดอร์ชั่วคราวของระบบ
2. สร้างโฟลเดอร์สำหรับงาน Deploy โดยใช้ชื่อที่กำหนดไว้
3. สร้างโฟลเดอร์ `public` ภายใน
4. เขียนเนื้อหา HTML ที่ Agent ส่งมาเป็นไฟล์
5. สร้างไฟล์ตั้งค่า `firebase.json`

โครงสร้างโดยแนวคิดเป็นดังนี้ โดยข้อความไม่ได้ระบุชื่อไฟล์ HTML ชัดเจน:

```text
โฟลเดอร์ชั่วคราว/
└── โฟลเดอร์สำหรับ Deploy/
    ├── firebase.json
    └── public/
        └── ไฟล์ HTML ที่สร้างขึ้น
```

**`firebase.json` ใช้ทำอะไร**

เป็นไฟล์ตั้งค่าให้ Firebase CLI ทราบรายละเอียดการ Deploy เช่น โฟลเดอร์ใดเก็บเนื้อหาเว็บไซต์ และไฟล์ใดควรถูกละเว้น ในตัวอย่าง โฟลเดอร์ `public` เป็นที่เก็บเนื้อหาเว็บที่จะนำขึ้น Hosting

ผู้บรรยายย้ำว่า เครื่องมือเหล่านี้สร้างขึ้นเพื่อแอปพลิเคชันนี้โดยเฉพาะ หากเลือกทำ Agent สำหรับงานอื่น ก็ต้องสร้างเครื่องมือที่ช่วยให้ Agent ทำงานนั้นได้

บทเรียนสำคัญคือ **เครื่องมือที่เชื่อมต่อให้ Agent เป็นตัวกำหนดว่ามันลงมือทำอะไรได้บ้าง**

### 7:32–8:36 — เครื่องมือ Deploy เว็บไซต์ทำงานอย่างไร

เครื่องมือ Deploy ใช้ไฟล์ที่บันทึกไว้แล้ว โดยทำงานตามลำดับ:

1. ตรวจว่ามีโฟลเดอร์สำหรับ Deploy หรือไม่
2. เตรียมค่าที่ต้องใช้ในการเรียก CLI
3. หา Project เป้าหมาย
4. สร้างคำสั่ง Deploy ไปยัง Firebase Hosting Preview Channel
5. เรียกคำสั่ง
6. รับผลลัพธ์และจัดการข้อผิดพลาด

หากหา Project จากตัวแปรสภาพแวดล้อมไม่ได้ จะใช้คำสั่ง:

```bash
gcloud config get-value project
```

เมื่อได้ Project แล้ว เครื่องมือจะระบุ Project เป้าหมายในคำสั่ง Deploy เพื่อให้ชัดเจนว่าจะนำเว็บไซต์ขึ้นที่ใด

ข้อความที่ส่งมาไม่ได้มีคำสั่ง Firebase แบบเต็ม จึงยังไม่สามารถคัดลอกไป Deploy ตามตัวอย่างได้โดยตรง

### 8:37–9:51 — ปรับ Instructions ให้เป็น Website Generator

โครงสร้าง Agent ส่วนใหญ่ยังเหมือนเดิม สิ่งที่เปลี่ยนสำคัญคือ **Instructions และ Tools**

คำสั่งใหม่มีสาระประมาณว่า:

> คุณเป็น Agent สำหรับสร้างเว็บไซต์ รับคำขอของผู้ใช้ ทำความเข้าใจบริบท แล้วสร้างหน้าเว็บหนึ่งหน้า โดยรวม HTML, CSS และ JavaScript ไว้ในเอกสารเดียว เมื่อผู้ใช้ขอให้นำขึ้นใช้งาน ให้บันทึกเนื้อหาก่อน แล้วจึง Deploy เว็บไซต์ที่บันทึกไว้

| ส่วน | หน้าที่ |
| --- | --- |
| **HTML** | โครงสร้างและเนื้อหา |
| **CSS** | รูปลักษณ์และการจัดหน้า |
| **JavaScript** | พฤติกรรมและการโต้ตอบ |

ทั้งหมดรวมอยู่ในไฟล์เดียวตามโจทย์ของตัวอย่าง

**ทำไมแยกเป็นสองเครื่องมือ**

ผู้บรรยายต้องการให้ Agent สร้างโค้ดแล้วส่งไปบันทึกเพียงครั้งเดียว จากนั้นเครื่องมือ Deploy อ่านไฟล์นั้นต่อได้

จึงไม่ต้องส่งโค้ดเว็บไซต์ทั้งชุดซ้ำให้เครื่องมือ Deploy อีกครั้ง ช่วยลดการส่งเนื้อหาซ้ำ และทำให้การสร้างไฟล์กับการนำขึ้น Hosting เป็นขั้นตอนที่แยกตรวจสอบได้

อย่างไรก็ตาม การแยกเครื่องมือไม่ได้รับประกันว่าโมเดลจะไม่สร้างเนื้อหาซ้ำเลย พฤติกรรมยังขึ้นกับ Instructions และการทำงานของ Agent

### 9:52–12:01 — เตรียม Firebase และสิทธิ์ที่จำเป็น

การแก้โค้ดอย่างเดียวไม่เพียงพอ สภาพแวดล้อมคลาวด์ต้องพร้อมด้วย ผู้บรรยายกล่าวถึงเงื่อนไขสำคัญสามข้อ

**1. เปิด Firebase Hosting API**

Project ต้องเปิดบริการที่จำเป็นเพื่อให้คำสั่ง Deploy ใช้งานได้ ข้อความไม่ได้ระบุคำสั่งเต็ม จึงต้องตรวจชื่อบริการจากเอกสารหรือโค้ดประกอบก่อนทำตาม

**2. ตัวตนที่เครื่องมือใช้ต้องมีสิทธิ์**

บัญชีผู้ใช้หรือ Service Account ที่ใช้เรียกบริการต้องได้รับสิทธิ์ Deploy ไปยัง Firebase Hosting ผู้บรรยายกล่าวถึงบทบาท **Firebase Hosting Admin**

ส่วนคำอธิบายในคลิปที่ว่า Owner หรือ Editor มีบทบาทนี้อยู่แล้ว ควรแยกความหมายว่า **บัญชีอาจมีสิทธิ์ที่เพียงพอผ่านบทบาทกว้างกว่า แต่ไม่ได้แปลว่าได้รับบทบาท Firebase Hosting Admin โดยตรง** และสิทธิ์จริงยังขึ้นกับนโยบายของโปรเจกต์หรือองค์กร

**3. เพิ่ม Firebase ให้ Google Cloud Project เดิม**

ต้องเข้า Firebase Console แล้วเลือกเพิ่ม Firebase ให้ Google Cloud Project ที่ใช้อยู่ เพื่อให้โปรเจกต์พร้อมใช้งานบริการ Firebase การมี Google Cloud Project อยู่แล้วจึงไม่ได้หมายความว่าตั้งค่า Firebase Hosting ครบแล้ว

ภาพรวมเงื่อนไขคือ:

**โค้ดมีเครื่องมือที่ถูกต้อง + โปรเจกต์เปิดบริการพร้อม + ตัวตนมีสิทธิ์ → จึง Deploy ได้**

ในตัวอย่าง ผู้บรรยายใช้ข้อมูลรับรองที่เตรียมไว้จากบทก่อน แต่เมื่อนำไปใช้งานจริงต้องตรวจด้วยว่า Firebase CLI กำลังใช้ข้อมูลรับรองชุดใด เพราะการยืนยันตัวตนของเครื่องมือแต่ละตัวอาจแตกต่างกันตามการตั้งค่า

### 12:02–13:35 — รัน Agent และสั่ง Deploy

ผู้บรรยายเข้าโฟลเดอร์ Website Generator เวอร์ชันสอง แล้วเปิด Playground ผ่าน Agents CLI เบื้องหลัง เครื่องมือเรียกคำสั่งลักษณะ:

```bash
uv run adk web
```

พร้อมตัวเลือก Host, Port และค่าอื่น ๆ ที่ CLI จัดการให้ เมื่อเปิดหน้าเว็บแล้ว ผู้ใช้สามารถดู Session เก่าหรือเริ่มสนทนาใหม่ได้

**เปิด Streaming**

ผู้บรรยายแนะนำให้เปิด Streaming เพราะการสร้างเว็บไซต์อาจใช้เวลา วิธีนี้ช่วยให้เห็นผลหรือเหตุการณ์ทยอยปรากฏระหว่างทำงาน Streaming ช่วยเรื่องการแสดงความคืบหน้า ไม่ได้หมายความว่าจะทำให้การสร้างเว็บไซต์เสร็จเร็วขึ้นโดยตัวมันเอง

**ถ้าบันทึกแล้วแต่ยังไม่ Deploy**

## สรุปท้ายเรื่อง

บทนี้สอนการต่อยอด Agent ด้วย **คำสั่งที่ตรงงานและเครื่องมือที่ลงมือทำได้จริง**

เส้นทางการทำงานหลักคือ:

**ผู้ใช้บอกโจทย์ → Agent สร้างหน้าเว็บ → เครื่องมือบันทึกไฟล์ → เครื่องมือ Deploy ขึ้น Firebase → ผู้ใช้ได้รับ URL**

| สิ่งที่เพิ่ม | ประโยชน์ |
| --- | --- |
| Instructions สำหรับสร้างเว็บไซต์ | กำหนดหน้าที่และรูปแบบผลลัพธ์ |
| เครื่องมือบันทึกเนื้อหา | เก็บโค้ดไว้ให้ขั้นตอนถัดไปใช้ |
| เครื่องมือ Deploy | เชื่อมการทำงานกับ Firebase Hosting |
| Preview Channel | แยกการทดสอบออกจากเว็บไซต์หลัก |
| การตั้งค่า API และสิทธิ์ | ทำให้เครื่องมือเข้าถึงบริการได้จริง |

สิ่งที่ควรจำเป็นพิเศษ:

- **ชื่อ Agent อย่างเดียวไม่เปลี่ยนความสามารถ** ต้องปรับ Instructions และเชื่อมเครื่องมือด้วย
- **ไฟล์ชั่วคราวไม่ได้เป็นที่เก็บถาวร** โดยเฉพาะเมื่อนำไปใช้บนระบบที่มีหลาย Instance หรือรีสตาร์ตได้
- **Preview Channel ยังอาจเข้าถึงได้ผ่านอินเทอร์เน็ต** การตั้งหมดอายุช่วยจำกัดช่วงเวลา แต่ไม่ได้แทนระบบควบคุมการเข้าถึง
- **Deploy เว็บไซต์กับ Deploy ตัว Agent เป็นคนละเรื่อง** บทนี้ทำส่วนแรกสำเร็จตามตัวอย่าง

หากจะลงมือทำตาม ยังต้องมีโค้ดประกอบสำหรับเครื่องมือทั้งสอง คำสั่ง Firebase ที่ครบ และรายละเอียดการตั้งค่า เพราะข้อความถอดเสียงอธิบายแนวทางได้ แต่ยังไม่ใช่คู่มือติดตั้งที่คัดลอกไปรันได้ครบ
