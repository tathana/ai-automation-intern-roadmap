บทที่ 4 — Deploy ตัว Agent ขึ้นคลาวด์

บทนี้พาจาก Agent ที่รันบนเครื่อง ไปสู่ Agent ที่รันบนคลาวด์ และปรับเครื่องมือสร้างเว็บไซต์ให้เหมาะกับสภาพแวดล้อมนั้น

ต่างจากบทก่อนที่นำเฉพาะเว็บไซต์ขึ้น Firebase Hosting บทนี้ Deploy ตัว Agent ด้วย จากนั้นทดสอบสั่งให้ Agent บนคลาวด์สร้างและเผยแพร่เว็บไซต์อีกทอดหนึ่ง

เนื้อหาอ้างอิงจากข้อความถอดเสียง ชื่อฟิลด์ คำสั่ง และพฤติกรรมบริการบางส่วนยังต้องตรวจเทียบกับโค้ดหรือเอกสารจริงก่อนนำไปใช้

เนื้อหาแบบละเอียด

0:00–3:21 — ทางเลือกในการ Deploy Agent มีอะไรบ้าง

ผู้บรรยายเริ่มจากสถานการณ์ที่ Agent ทำงานบนเครื่องได้แล้ว เช่น สร้างเว็บไซต์ บันทึกไฟล์ และนำเว็บไซต์ขึ้น Hosting ได้ แต่หากต้องการให้คนอื่นเรียกใช้งานโดยไม่ต้องพึ่งเครื่องของผู้พัฒนา ก็ต้องนำตัว Agent ขึ้นคลาวด์

ในคลิปแบ่งทางเลือกหลักเป็นสามกลุ่ม:

ทางเลือก แนวคิด ตัวอย่างที่กล่าวถึง
Compute เตรียมทรัพยากรประมวลผลและดูแลสภาพแวดล้อมเองมากขึ้น เครื่องประมวลผลบนคลาวด์
Serverless นำแอปไปรันบนบริการที่จัดการโครงสร้างพื้นฐานให้ Google Cloud Run
Managed Agent Runtime ใช้บริการที่ออกแบบมารองรับการรัน Agent โดยเฉพาะ Google Agent Runtime ตามชื่อในคลิป

การแบ่งนี้เป็นกรอบอธิบายเพื่อให้เริ่มเข้าใจง่าย แต่กลุ่มต่าง ๆ อาจทับซ้อนกันได้ เช่น Managed Runtime อาจใช้โครงสร้างพื้นฐานแบบ Serverless อยู่เบื้องหลัง

ผู้บรรยายเน้นว่า การเลือกวิธี Deploy ส่งผลต่อ:

  • Latency — ระยะเวลารอผลลัพธ์
  • Cost — ค่าใช้จ่าย
  • Security — การควบคุมสิทธิ์และความปลอดภัย
  • Scaling — การรองรับปริมาณงานที่เพิ่มขึ้น

แม้ชื่อบทเปิดด้วยสามทางเลือก แต่เนื้อหาส่วนใหญ่จะสาธิต Managed Agent Runtime ไม่ได้เปรียบเทียบ Compute และ Cloud Run อย่างละเอียด ช่วงท้ายของส่วนนี้เป็นการแนะนำช่องและคอร์สประกอบ ไม่มีขั้นตอนทางเทคนิคเพิ่มเติม

3:22–4:21 — แผน Deploy สี่ขั้นตอน

ผู้บรรยายวางกระบวนการไว้ดังนี้:

  1. ทำความเข้าใจ Manifest — ตรวจไฟล์ตั้งค่าที่ CLI ใช้อ่านข้อมูลโปรเจกต์และเป้าหมายการ Deploy
  2. กำหนดตัวตนและสิทธิ์ของ Agent — สร้าง Service Account และให้สิทธิ์ที่จำเป็น
  3. Deploy ไปยัง Agent Runtime — ใช้ Manifest ร่วมกับ Service Account
  4. ทดสอบจาก Google Cloud Console — เปิด Playground ของ Agent ที่ Deploy แล้ว และสั่งงานจริง

หัวใจคือ ต้องเตรียมให้ครบทั้ง โค้ด การตั้งค่า และสิทธิ์ของตัวตนที่ใช้รัน

4:22–8:17 — ขั้นที่ 1: ทำความเข้าใจ Manifest

Manifest เป็นไฟล์ตั้งค่าที่ CLI สร้างไว้ตั้งแต่ตอนสร้างโครงโปรเจกต์ Website Generator ในบทก่อน

ข้อความถอดเสียงสะกดชื่อไฟล์ไม่สม่ำเสมอ จึงควรดูชื่อจริงในโปรเจกต์ โดยเป็นไฟล์ Manifest รูปแบบ YAML ของ Agents CLI

ฟิลด์หรือรายการ ความหมายตามคลิป
Name ชื่อโปรเจกต์ Agent เช่น Website Generator
CLI Version เวอร์ชัน CLI ที่ใช้สร้างโครงโปรเจกต์
Agent Directory ตำแหน่งโค้ด Agent เช่นโฟลเดอร์ app
Region ภูมิภาคที่จะนำระบบขึ้นใช้งาน
Base Template แม่แบบเริ่มต้น เช่น ADK
Generated At วันเวลาที่สร้างโปรเจกต์
Language ภาษาหลักของโปรเจกต์ เช่น Python
Create Params ตัวเลือกที่ใช้ตอนสร้างโครงโปรเจกต์

Name และ CLI Version

ชื่อโปรเจกต์ใช้เป็นตัวระบุเริ่มต้นในขั้นตอน Deploy หรือการลงทะเบียนบางส่วน ส่วนเวอร์ชัน CLI เป็นข้อมูลอ้างอิงว่าตอนสร้างโปรเจกต์ใช้เครื่องมือเวอร์ชันใด ช่วยในการตรวจสอบความเข้ากันได้ แต่ไม่ได้รับประกันว่า CLI ทุกเวอร์ชันในอนาคตจะทำงานร่วมกันได้เสมอ

Agent Directory

เป็นตำแหน่งโค้ดเมื่อเทียบจากโฟลเดอร์โปรเจกต์ ในตัวอย่างคือ app ซึ่งมีไฟล์นิยาม Agent อยู่ภายใน

Region

ในตัวอย่างเดิมมีค่า us-east1 และผู้บรรยายเปลี่ยนเป็น asia-south1 เพราะมีทรัพยากรอื่นอยู่ในภูมิภาคนั้นแล้ว แนวคิดคือเลือกตำแหน่งให้สอดคล้องกับระบบที่เกี่ยวข้อง แต่เมื่อใช้งานจริงยังต้องตรวจด้วยว่า Runtime และโมเดลที่ต้องการรองรับ Region นั้นหรือไม่

Base Template และ Language

ระบุว่าโปรเจกต์เริ่มจากแม่แบบ ADK และใช้ Python เป็นภาษาหลัก

Deployment Target

ในตัวอย่างเลือก Agent Runtime ผู้บรรยายกล่าวถึง Cloud Run และ GKE เป็นทางเลือกอื่นด้วย แต่ไม่ได้สาธิตในบทนี้

Session Type

ค่าเดิมเป็น none และผู้บรรยายเปลี่ยนเป็นค่าที่เรียกในเสียงประมาณ “in-core memory” ซึ่งอาจหมายถึงการเก็บ Session ในหน่วยความจำ ต้องตรวจชื่อค่าที่ CLI รองรับจริงจากไฟล์หรือเอกสารประกอบ

สิ่งที่ควรเข้าใจคือ:

  • การไม่ตั้งที่เก็บ Session ไม่ได้แปลว่าทุก Runtime จะจัดการประวัติเหมือนกัน
  • การเก็บในหน่วยความจำไม่ใช่ความจำถาวร
  • หากมีหลาย Instance แต่ละ Instance อาจไม่ได้ใช้ข้อมูลในหน่วยความจำร่วมกัน

อีกทั้งในคลิปภายหลังมีหน้าประวัติ Sessions ของบริการ จึงต้องแยกการตั้งค่า Session ของแอปออกจากความสามารถที่ Runtime จัดการให้

CI/CD Runner

ตัวอย่างข้ามการตั้งค่าระบบ Deploy อัตโนมัติไว้ก่อน

A2A

ผู้บรรยายอธิบายว่าค่าเปิดใช้งานเกี่ยวข้องกับการเปิด Endpoint สำหรับการสื่อสารระหว่าง Agent ผ่านโปรโตคอล A2A อย่างไรก็ตาม รายละเอียดว่า Endpoint ใดถูกสร้างและเข้าถึงได้อย่างไรขึ้นกับแม่แบบและ Runtime ที่ใช้ ไม่ได้หมายความว่าจะเปิดสาธารณะโดยไม่มีการควบคุมสิทธิ์

Agent Gateway

ในตัวอย่างเป็น false ผู้บรรยายอธิบายว่าไม่ได้วาง Agent ไว้หลัง Gateway กลางสำหรับงานอย่างการส่งต่อคำขอหรือบังคับใช้นโยบาย

Agent Guidance File

กล่าวถึงไฟล์ Markdown สำหรับแนวทางการทำงาน โดยข้อความถอดเสียงมีชื่อคล้าย GEMINI.md ต้องตรวจการใช้งานจริงของ CLI ด้วย เพราะไฟล์แนวทางสำหรับเครื่องมือพัฒนาไม่ได้กลายเป็น Instructions ของ Agent ที่รันจริงโดยอัตโนมัติเสมอไป

8:18–11:09 — ขั้นที่ 2: สร้างตัวตนและกำหนดสิทธิ์

ผู้บรรยายใช้ Service Account เป็นตัวตนของ Agent ที่รันบนคลาวด์ เป็นบัญชีสำหรับโปรแกรมหรือระบบ เพื่อให้บริการรู้ว่าคำขอมาจากตัวตนใด และควรได้รับสิทธิ์อะไร

ลำดับการเตรียมมีดังนี้:

  1. อ่าน Project ID ที่ตั้งไว้
  2. กำหนดชื่อ Service Account
  3. สร้าง Service Account
  4. เพิ่มบทบาทที่ Agent ต้องใช้

อีเมลของ Service Account มีรูปแบบ:

SERVICE_ACCOUNT_NAME@PROJECT_ID.iam.gserviceaccount.com

ผู้บรรยายสร้างบัญชีด้วยคำสั่งกลุ่ม:

gcloud iam service-accounts create ...

โดยใส่ชื่อ คำอธิบาย และชื่อที่แสดงในระบบ

บทบาท ใช้เพื่อ
Vertex AI User — roles/aiplatform.user เรียกใช้ความสามารถของ Vertex AI ตามสิทธิ์ของบทบาท
Firebase Hosting Admin จัดการการนำเว็บไซต์ขึ้น Firebase Hosting

การกำหนดบทบาททำผ่านคำสั่งกลุ่ม:

gcloud projects add-iam-policy-binding ...

เมื่อจบขั้นนี้ Agent จะมีตัวตนสำหรับเรียกโมเดลและใช้เครื่องมือ Deploy เว็บไซต์

ต้องแยกตัวตนสองฝ่าย

ฝ่าย หน้าที่
ผู้สั่ง Deploy สร้างหรืออัปเดตระบบบนคลาวด์
Service Account ของ Agent ใช้สิทธิ์ระหว่าง Agent กำลังทำงาน

บทบาทสองรายการข้างต้นเน้นสิทธิ์ระหว่างรัน ส่วนผู้สั่ง Deploy อาจต้องมีสิทธิ์เพิ่มเติม รวมถึงสิทธิ์ใช้ Service Account นั้นด้วย ข้อความไม่ได้แจกแจงสิทธิ์สำหรับกระบวนการ Deploy ครบทุกส่วน

การสร้าง Service Account เพียงอย่างเดียวยังไม่ทำให้ Agent ใช้มันทันที ต้องระบุผูกกับ Runtime ในขั้นต่อไป

11:10–12:47 — ขั้นที่ 3: Deploy ไปยัง Agent Runtime

ผู้บรรยายใช้คำสั่ง Deploy ของ Agents CLI พร้อมระบุ Service Account ที่จะใช้เป็นตัวตนของ Agent, Google Cloud Project เป้าหมาย และโหมด Interactive

ข้อความไม่ได้แสดงชื่อคำสั่งและแฟล็กทั้งหมดชัดเจน จึงยังเขียนคำสั่งพร้อมรันให้ตรงกับ CLI นี้ไม่ได้

โหมด Interactive ทำอะไร

CLI จะถามข้อมูลหรือขอให้ตรวจสอบก่อนดำเนินการ เช่น ยืนยันว่าจะ Deploy ไปยัง Project ที่แสดงหรือไม่ หน้าจอแสดงข้อมูลประกอบ ได้แก่:

  • Project
  • Location หรือ Region
  • จำนวน Instance ต่ำสุดและสูงสุด
  • Environment Variables
  • สถานะการสร้าง Agent

ผู้บรรยายระบุว่าในประสบการณ์ของตน ใช้เวลาประมาณ 5–10 นาที ซึ่งเป็นเวลาของตัวอย่าง ไม่ใช่เวลาที่รับประกันสำหรับทุกครั้ง

หาก Terminal ถูกยกเลิกหรือหลุดระหว่างทาง สามารถใช้คำสั่งตรวจสถานะที่ CLI แสดงไว้ได้ การหยุดรอใน Terminal ไม่ได้แปลว่างานฝั่งคลาวด์ถูกยกเลิกเสมอไป

12:48–13:45 — ขั้นที่ 4: ตรวจสอบและทดสอบบนคลาวด์

เมื่อ Deploy สำเร็จ CLI แสดงลิงก์ไปยัง Google Cloud Console ผู้บรรยายเปิดหน้ารายการ Deployments แล้วเลือก Website Generator ที่เพิ่งสร้าง จากนั้นตรวจสอบ:

  • Identity — ตัวตนที่ Runtime ใช้
  • Resource — ข้อมูลระบุทรัพยากร
  • Agent Runtime ID — ตัวระบุ Agent สำหรับใช้อ้างอิงกับระบบอื่น

ตัวระบุแบบเต็มเริ่มด้วยเส้นทางลักษณะ projects/... แต่ข้อความไม่ได้ให้รูปแบบทั้งหมด จึงไม่ควรเดาต่อจากส่วนที่ขาด

จากนั้นเปิด Playground บนคลาวด์ แล้วส่งคำขอประมาณว่า:

สร้างหน้า Hello World แบบง่าย และ Deploy ด้วย Unified Deploy Tool

จุดนี้เป็นการทดสอบ Agent ที่รันอยู่บนคลาวด์แล้ว ต่างจาก Playground บนเครื่องในบทก่อน

13:46–15:26 — ทำไมต้องเปลี่ยนเป็น Unified Deploy Tool

บทก่อนแยกเครื่องมือเป็นสองขั้น คือบันทึกไฟล์เว็บไซต์ แล้วอ่านไฟล์นั้นเพื่อ Deploy

เมื่อย้ายขึ้นสภาพแวดล้อมที่อาจมีหลาย Instance การอาศัยไฟล์ชั่วคราวร่วมกันระหว่างสอง Tool Calls อาจมีปัญหา เช่น:

  • การเรียกครั้งถัดไปไปรันคนละ Instance
  • Instance เดิมถูกรีสตาร์ต
  • ไฟล์ชั่วคราวไม่พร้อมใช้งานแล้ว

ไม่ได้หมายความว่าไฟล์จะหายทุกครั้ง แต่หมายถึง ไม่ควรสมมติว่าไฟล์ในเครื่องจะพร้อมให้ Tool Call ถัดไปเสมอ

ผู้บรรยายจึงรวมงานเป็นเครื่องมือเดียว:

รับ HTML → เตรียมข้อมูลหรือไฟล์ → Deploy → คืน URL

การทำให้อยู่ภายในการเรียกฟังก์ชันเดียวช่วยลดการพึ่งพาสถานะข้าม Tool Calls แต่ไม่ได้ทำให้กระบวนการทั้งหมดกลายเป็นธุรกรรมที่สำเร็จหรือยกเลิกพร้อมกัน หากล้มเหลวกลางทางก็ยังต้องจัดการข้อผิดพลาด

ในตัวอย่าง Agent สร้างหน้า Hello World และส่ง URL ของ Firebase Hosting Preview Channel กลับมาได้ ผู้บรรยายเปิดดูหน้าเว็บซึ่งมีปุ่มแสดงเอฟเฟกต์และตัวเลือกภาษา นอกจากนี้ยังแสดงหน้าประวัติ Sessions ของ Agent ที่ Deploy แล้ว

15:27–16:31 — Unified Tool: ใช้ตัวตนของ Runtime เรียก API

การเปลี่ยนแปลงสำคัญอีกอย่างคือ จากเดิมที่ใช้ Firebase CLI มาเป็นการเรียก Firebase Hosting REST API โดยตรง

ผู้บรรยายระบุว่า แนวทางนี้ช่วยหลีกเลี่ยงความยุ่งยากในการ Login แบบเปิดเบราว์เซอร์บนสภาพแวดล้อมที่ไม่มีหน้าจอให้ผู้ใช้โต้ตอบ ขั้นตอนโดยแนวคิดคือ:

  1. อ่าน Project ID จาก Environment Variable
  2. ขอข้อมูลรับรองของ Service Account ที่ผูกกับ Runtime
  3. ขอ OAuth Access Token
  4. แนบ Token ใน Authorization Header เพื่อเรียก API
Authorization: Bearer ACCESS_TOKEN

ในสภาพแวดล้อม Google Cloud ที่รองรับ ตัวไลบรารีสามารถรับข้อมูลรับรองผ่าน Metadata Server ของระบบได้ จึงไม่จำเป็นต้องนำไฟล์กุญแจ Service Account มาใส่ในโค้ด

สิทธิ์ที่ Token ใช้งานได้ยังขึ้นกับ Service Account และนโยบายที่กำหนดไว้ การมี Token ไม่ได้ทำให้ข้ามข้อจำกัด IAM ได้

ทั้งนี้ Firebase CLI สามารถทำงานแบบไม่โต้ตอบได้ในบางการตั้งค่าเช่นกัน การใช้ REST API เป็นทางเลือกที่ผู้บรรยายเลือกสำหรับตัวอย่างนี้

16:32–17:06 — เตรียมเนื้อหาและ Hash ก่อนอัปโหลด

ก่อนส่งเว็บไซต์ขึ้น Firebase Hosting เครื่องมือต้องเตรียม:

  • เนื้อหา HTML ในรูป Bytes
  • ข้อมูลที่บีบอัดด้วย gzip
  • ค่า SHA-256 Hash ตามข้อกำหนด API

Hash ทำหน้าที่เป็นลายนิ้วมือของเนื้อหา เพื่อให้ Firebase ตรวจได้ว่ามีข้อมูลชุดนั้นอยู่แล้วหรือจำเป็นต้องอัปโหลดใหม่

รายละเอียดว่าคำนวณ Hash จากข้อมูลขั้นใดและอัปโหลดในรูปแบบใดต้องทำตามข้อกำหนดของ Hosting API ให้ตรงกัน ข้อความนี้ยังไม่มีโค้ดครบสำหรับตรวจสอบ ประโยชน์คือระบบสามารถหลีกเลี่ยงการอัปโหลดเนื้อหาที่มีอยู่แล้วได้

17:07–18:20 — ลำดับ Deploy ผ่าน Firebase Hosting REST API

ขั้น การทำงาน
1. สร้าง Version สร้างชุดข้อมูลเว็บไซต์ที่จะเผยแพร่
2. แจ้งรายการไฟล์และ Hash บอกว่า Version นี้ประกอบด้วยไฟล์อะไรบ้าง
3. ตรวจไฟล์ที่ขาด Firebase ส่งกลับว่าต้องอัปโหลดเนื้อหาใด
4. อัปโหลด ส่งข้อมูลที่ระบบยังไม่มีไปยัง Upload Endpoint
5. Finalize Version ปิดการเตรียม Version ให้พร้อมนำไปเผยแพร่
6. เตรียม Preview Channel สร้างหรืออัปเดตช่องทางดูตัวอย่าง
7. Release ทำให้ Preview Channel ชี้ไปยัง Version ใหม่

Version กับ Release ต่างกันอย่างไร

  • Version คือชุดเนื้อหาเว็บไซต์ที่เตรียมไว้
  • Release คือการนำ Version นั้นไปใช้กับช่องทางเผยแพร่

จึงต้องเตรียมและ Finalize เนื้อหา ก่อนนำไป Release

การตั้งค่า Cache

ผู้บรรยายกล่าวถึงการตั้ง Cache-Control เป็นศูนย์เพื่อให้เห็นการเปลี่ยนแปลงได้เร็วขึ้น แต่การตั้งค่าอย่าง max-age=0 ไม่ได้แปลว่าไม่มีการเก็บ Cache เลย โดยทั่วไปเกี่ยวข้องกับการทำให้ข้อมูลหมดความสดทันทีและต้องตรวจสอบใหม่ รายละเอียดจริงขึ้นกับ Header และพฤติกรรมของ Hosting

อายุ Preview Channel

ตัวอย่างระบุ 1,800 วินาที หรือ 30 นาที และกล่าวถึงการใช้คำขอ PATCH เพื่อปรับ TTL อย่างไรก็ตาม ต้องตรวจสอบข้อกำหนด API ปัจจุบัน ทั้งชื่อฟิลด์ ระยะเวลาที่รองรับ และวิธีสร้าง Channel หากยังไม่มี เพราะคำขออัปเดตไม่ได้สร้างทรัพยากรใหม่ให้อัตโนมัติในทุก API

หากใช้ชื่อ Channel เดิมซ้ำ การ Release ครั้งใหม่ก็อาจเปลี่ยนเว็บไซต์ที่ URL เดิมกำลังแสดงอยู่

18:21–18:53 — ขอบเขตของตัวอย่างและจบบท

ผู้บรรยายระบุว่า เป้าหมายของคอร์สคือการเรียนรู้แพลตฟอร์ม Agent ไม่ใช่การสอน Firebase Hosting API แบบครบถ้วน

โค้ดเครื่องมือ Deploy เป็นตัวอย่างเฉพาะแอปพลิเคชันนี้ และผู้บรรยายใช้ Gemini ช่วยสร้างและทำความเข้าใจโค้ดด้วย

สิ่งที่ต้องนำไปประยุกต์คือ:

  • Agent ต้องมีเครื่องมือที่ตรงกับงาน
  • เครื่องมือต้องทำงานได้ในสภาพแวดล้อมที่ Deploy จริง
  • ตัวตนของ Agent ต้องมีสิทธิ์เรียกบริการนั้น
  • การย้ายจากเครื่องส่วนตัวขึ้นคลาวด์อาจต้องปรับวิธีเก็บสถานะและยืนยันตัวตน

สิ่งที่ควรจำมากที่สุดมีสามข้อ:

  1. สิทธิ์ของผู้ Deploy กับสิทธิ์ของ Agent เป็นคนละส่วน ต้องเตรียมให้ถูกทั้งสองฝ่าย
  2. อย่าพึ่งไฟล์ชั่วคราวข้าม Tool Calls โดยไม่มีหลักประกัน การทำงานบนคลาวด์อาจเปลี่ยน Instance ได้
  3. Deploy สำเร็จต้องทดสอบเครื่องมือจริงด้วย การที่ Agent ตอบข้อความได้ยังไม่ยืนยันว่ามีสิทธิ์เรียกโมเดลและเผยแพร่เว็บไซต์ครบทุกขั้น

เมื่อจบบทตามการสาธิต ผู้บรรยายมี Agent บนคลาวด์ที่รับคำขอ สร้างหน้าเว็บ และส่ง URL เว็บไซต์ที่เผยแพร่แล้วกลับมาได้
