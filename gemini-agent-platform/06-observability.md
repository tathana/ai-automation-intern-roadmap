# บทที่ 6 — Observability และ Traces

บทนี้สอน **เปิดการติดตามการทำงานของ Agent เพื่อดูว่าแต่ละคำขอผ่านขั้นตอนใด ใช้เวลาเท่าไร และควรปรับปรุงตรงไหน** โดยใช้ Observability, OpenTelemetry และ Traces

ต่อจากบทก่อนที่สร้าง Deploy และเพิ่มการตรวจความปลอดภัยแล้ว บทนี้เข้าสู่ส่วน **Optimize — การปรับปรุงระบบจากข้อมูลการทำงานจริง**

เนื้อหาเรียบเรียงแบบละเอียดตามเวลา จากข้อความถอดเสียง พร้อมสรุปท้ายเรื่อง โดยชื่อ Environment Variables บางตัวไม่มีอยู่ครบในข้อความ จึงยังไม่สามารถจัดเป็นชุดค่าที่คัดลอกไปรันได้ทันที

## เนื้อหาแบบละเอียด

### 0:00–0:56 — จากการสร้างระบบ สู่การปรับปรุงระบบ

ผู้บรรยายทบทวนสิ่งที่ทำมาแล้วในคอร์ส:

1. ทำความเข้าใจแพลตฟอร์ม
2. เตรียมสภาพแวดล้อม
3. สร้าง Agent ด้วย ADK บนเครื่อง
4. ปรับ Agent ให้สร้างเว็บไซต์ได้
5. Deploy ตัว Agent ขึ้น Runtime
6. ใช้ Console, Playground และ Sessions
7. กำหนดตัวตนให้ Agent
8. ตั้งค่า Model Armor

ขั้นต่อไปคือเปิด **Observability และ Traces** เพื่อให้มีข้อมูลสำหรับตรวจสอบและปรับปรุง Agent

ผู้บรรยายระบุว่าบทนี้เป็นช่วงท้ายของเนื้อหาหลัก และจะมีบทเสริมเกี่ยวกับประเด็นเฉพาะสำหรับสร้าง Agent ที่แข็งแรงขึ้น

### 0:57–1:41 — Observability, Telemetry และ Tracing ต่างกันอย่างไร

ผู้บรรยายอธิบายว่า Observability คือการใช้ข้อมูลที่ระบบส่งออกมา เพื่อทำความเข้าใจสุขภาพและพฤติกรรมของ Agent ที่ Deploy แล้ว

| คำ | ความหมายในบริบทนี้ |
| --- | --- |
| **Telemetry** | ข้อมูลการทำงานที่ระบบเก็บและส่งออกมา |
| **Metrics** | ค่าตัวเลขสำหรับดูภาพรวม เช่น จำนวนการเรียกใช้และระยะเวลา |
| **Logs** | บันทึกเหตุการณ์หรือข้อความระหว่างทำงาน |
| **Traces** | ข้อมูลเชื่อมโยงขั้นตอนต่าง ๆ ของการประมวลผลคำขอ |
| **Observability** | การใช้ข้อมูลเหล่านี้ทำความเข้าใจและวิเคราะห์ระบบ |

**Trace ช่วยตอบคำถามอะไร**

- คำขอนี้เรียกโมเดลกี่ครั้ง
- เรียกเครื่องมือใดบ้าง
- ขั้นตอนไหนใช้เวลานาน
- ข้อผิดพลาดเกิดตรงไหน
- ลำดับการทำงานเป็นไปตามที่คาดหรือไม่

ผู้บรรยายกล่าวถึงการแสดงผลเป็นกราฟแบบ **DAG — Directed Acyclic Graph** ซึ่งช่วยแสดงความสัมพันธ์และลำดับของขั้นตอน

อย่างไรก็ตาม คำอธิบายในคลิปที่ว่าเห็น “Reasoning Loop” ควรเข้าใจว่า **เห็นขั้นตอนและเหตุการณ์ที่ระบบบันทึกไว้** เช่น การเรียกโมเดลและเครื่องมือ ไม่ใช่การเห็นกระบวนการคิดภายในทั้งหมดของโมเดล

เพื่อเก็บข้อมูลเหล่านี้ ผู้บรรยายใช้ **OpenTelemetry** ซึ่งเป็นมาตรฐานและชุดเครื่องมือสำหรับสร้างและส่งข้อมูลติดตามระบบ

### 1:42–2:45 — ตั้งค่า Environment Variables

ผู้บรรยายกลับไปยังโปรเจกต์ Website Generator เวอร์ชันสอง แล้วเปิดใน IDE เช่น Antigravity หรือ VS Code การตั้งค่ามีสามส่วนหลัก:

1. เปิด Telemetry ของ Runtime
2. เปิดการเก็บข้อมูลที่เกี่ยวกับการเรียกโมเดล
3. เปิดการเก็บเนื้อหาข้อความจริง

จากเสียงที่ถอดมา ตัวแปรแรกน่าจะเป็น:

```dotenv
GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true
```

ส่วนตัวแปรอีกสองตัว **ไม่มีชื่อเต็มอยู่ในข้อความที่ส่งมา** โดยผู้บรรยายเน้นว่าต้องใส่ค่าตามรูปแบบที่กำหนด และหนึ่งในนั้นใช้ค่าประมาณ `event_only` แทนการตั้งทุกตัวเป็น `true`

ประเด็นสำคัญคือ Environment Variable แต่ละตัวอาจรับค่าคนละชนิด:

| รูปแบบค่า | ตัวอย่างความหมาย |
| --- | --- |
| Boolean | เปิดหรือปิด เช่น `true` |
| ค่าตัวเลือกเฉพาะ | เลือกวิธีบันทึก เช่น บันทึกเป็น Event |

หากใส่ `true` ให้ตัวแปรที่ต้องการค่าตัวเลือกเฉพาะ อาจทำให้การตั้งค่าไม่ถูกต้อง จึงต้องดูชื่อและค่าจริงจากโค้ดหรือ README ประกอบ ไม่ควรเดาจากข้อความถอดเสียง

**การเก็บเนื้อหาข้อความมีผลอย่างไร**

นอกจากเวลาและจำนวน Token แล้ว ระบบอาจบันทึก Prompt หรือข้อความที่ใช้ในการทำงานด้วย ขึ้นกับการตั้งค่าและส่วนประกอบที่รองรับ

ข้อมูลเหล่านั้นอาจมีข้อมูลผู้ใช้หรือเนื้อหาภายใน จึงต้องกำหนดสิทธิ์เข้าถึงบันทึกและเลือกเก็บให้เหมาะกับงาน ไม่จำเป็นต้องเปิดเก็บเนื้อหาทั้งหมดเพื่อดู Latency เสมอไป

### 2:46–4:48 — เพิ่มสิทธิ์เขียน Logs และ Traces

ผู้บรรยายใช้ Service Account ตัวเดิมที่ผูกกับ Agent แล้วเพิ่มบทบาทอีกสองรายการ:

| บทบาท | Role ID | หน้าที่ |
| --- | --- | --- |
| **Logs Writer** | `roles/logging.logWriter` | เขียนบันทึกลง Cloud Logging |
| **Cloud Trace Agent** | `roles/cloudtrace.agent` | ส่งข้อมูล Trace ไปยัง Cloud Trace |

**Logs Writer**

ผู้บรรยายอธิบายถึงสิทธิ์:

```text
logging.logEntries.create
```

ช่วยให้แอปพลิเคชันที่รันด้วย Service Account นี้ส่งบันทึกระบบและแอปพลิเคชันไปยัง Cloud Logging ประเด็นคือให้สิทธิ์สำหรับเขียน โดยไม่จำเป็นต้องให้สิทธิ์อ่านหรือลบบันทึกทั้งหมด

**Cloud Trace Agent**

ใช้ส่งข้อมูล Trace เช่น ขั้นตอนที่คำขอผ่านและเวลาที่ใช้ในแต่ละส่วน ในคลิปกล่าวถึงสิทธิ์:

```text
cloudtrace.traces.patch
```

ผู้บรรยายกำหนด Project ID แล้วใช้คำสั่งเพิ่ม IAM Policy Binding ให้ Service Account ข้อความไม่ได้มีคำสั่งเต็ม แต่โครงสร้างงานคือ:

**เลือก Project → ระบุ Service Account → เพิ่ม Logs Writer → เพิ่ม Cloud Trace Agent**

เมื่อเสร็จแล้ว ระบบจะมีทั้งการตั้งค่าให้สร้างและส่ง Telemetry และสิทธิ์ให้ตัวตนของ Agent เขียนข้อมูลดังกล่าว

สองส่วนนี้ต้องทำงานร่วมกัน การให้สิทธิ์อย่างเดียวไม่ได้สร้าง Trace ให้อัตโนมัติ และการเปิด Telemetry อย่างเดียวก็อาจส่งข้อมูลไม่สำเร็จหากไม่มีสิทธิ์

### 4:49–5:22 — Deploy Agent พร้อมค่าตั้งค่าใหม่

หลังเปลี่ยน Environment Variables และเพิ่มสิทธิ์แล้ว ผู้บรรยาย Deploy Agent อีกครั้งด้วยคำสั่งจาก README

ใช้โหมด **Interactive** เพื่อให้ CLI แสดงคำถามและตรวจสอบ Project กับค่าที่เกี่ยวข้องก่อนดำเนินการ ผู้บรรยายระบุว่าอาจใช้เวลาประมาณห้านาที ซึ่งเป็นเวลาโดยประมาณของตัวอย่าง

สิ่งสำคัญคือค่าที่แก้ต้องถูกส่งไปยัง **สภาพแวดล้อมของ Agent บนคลาวด์จริง** การแก้ไฟล์บนเครื่องเพียงอย่างเดียวไม่ได้ยืนยันว่า Runtime ที่ Deploy อยู่ได้รับค่าใหม่แล้ว

### 5:23–6:13 — สร้างคำขอทดสอบ

เมื่อ Deploy สำเร็จ ผู้บรรยายเปิดลิงก์ Console เลือก Website Generator แล้วเข้า Playground คำขอทดสอบมีใจความว่า:

> สร้าง Landing Page สำหรับบริษัทที่ขายเครื่องชงกาแฟคุณภาพสูง มีปุ่ม Call to Action ให้ผู้สนใจกรอกอีเมลและเข้าร่วมรายชื่อรอสำหรับเครื่องรุ่นใหม่ พร้อมเพิ่มรายละเอียดที่เหมาะสม

เป้าหมายของการทดสอบครั้งนี้มีสองด้าน:

1. ตรวจว่า Agent ยังสร้างและ Deploy เว็บไซต์ได้
2. ตรวจว่าเกิดข้อมูล Events และ Traces ให้ดูหรือไม่

การมีช่องกรอกอีเมลบนหน้าเว็บยังไม่ได้ยืนยันว่ามีระบบบันทึกอีเมลจริง เพราะคลิปไม่ได้สาธิต Backend หรือการจัดเก็บข้อมูลของ Waitlist

### 6:14–7:01 — ดู Trace ระหว่างทำงานและเปิดเว็บไซต์

ระหว่าง Agent ทำงาน ผู้บรรยายเปิดแท็บ Traces และเริ่มเห็นข้อมูลของคำขอปรากฏ

Agent เรียกเครื่องมือ **Unified Deploy Tool** จากบทก่อน จากนั้นรายงานว่า Deploy เว็บไซต์สำเร็จและส่ง URL กลับมา

ผู้บรรยายเปิดเว็บไซต์ตัวอย่าง ซึ่งมีชื่อแบรนด์ที่ Agent สร้างให้ ปุ่ม CTA สำหรับจองสิทธิ์หรือเข้าร่วมรายชื่อรอ ภาพกาแฟ และข้อมูลคุณสมบัติของสินค้า

ในบริบทของบทนี้ เว็บไซต์ทำหน้าที่เป็นงานตัวอย่างที่ใช้สร้างข้อมูลติดตามการทำงาน ไม่ใช่เป้าหมายหลักของการสอน

### 7:02–7:33 — ดู Metrics บน Dashboard

ผู้บรรยายเปิด Dashboard และ Refresh เพื่อดูค่าจากการทดสอบ ค่าที่ปรากฏตามคลิปคือ:

| Metric | ค่าที่แสดง |
| --- | --- |
| Sessions | 1 |
| Average Turns per Session | 1 |
| Agent Invocations | 3 |

จุดที่น่าสนใจคือ **ผู้ใช้ส่งคำขอหนึ่งครั้ง แต่จำนวน Agent Invocations อาจมากกว่าหนึ่ง**

ไม่ควรตีความทันทีว่า Agent ทำงานซ้ำผิดพลาด เพราะตัวนับอาจรวมการเรียกภายในตามนิยามของแพลตฟอร์ม ต้องดูรายละเอียด Metric และ Trace ประกอบ

ในทำนองเดียวกัน จำนวน Session จำนวน Turn จำนวน Agent Invocation และจำนวน Model Call เป็นคนละหน่วย และไม่จำเป็นต้องมีค่าเท่ากัน

Dashboard เหมาะสำหรับดูภาพรวม ส่วนการหาว่าแต่ละคำขอเกิดอะไรขึ้นต้องลงไปดู Trace

### 7:34–8:32 — เปิด Trace เพื่อดูลำดับการทำงาน

หน้าที่ผู้บรรยายใช้มีทั้ง:

- **Session View** — ดูการสนทนา
- **Trace View** — ดูข้อมูลการประมวลผลที่เกี่ยวข้อง

Session หนึ่งอาจมีหลาย Trace ได้ ขึ้นกับการแบ่งคำขอและการเก็บข้อมูลของระบบ เมื่อเปิด Trace จะเห็นกราฟขั้นตอนตั้งแต่เริ่มจนจบ เช่น:

1. เริ่ม Workflow ของ Website Generator
2. เรียกโมเดลภาษา
3. โมเดลสร้างเนื้อหา
4. เรียก Unified Deploy Tool
5. ประมวลผลต่อจนได้ผลลัพธ์

ชื่อเหตุการณ์ที่กล่าวถึงมีลักษณะเช่น:

```text
invoke_workflow
call_llm
generate_content
execute_tool
```

ชื่อจริงขึ้นกับ Instrumentation และเวอร์ชันที่ใช้ ข้อความถอดเสียงมีชื่อโมเดลที่อาจคลาดเคลื่อน จึงควรดู Model ID จากข้อมูลจริงใน Trace หากต้องการตรวจว่า Agent ใช้โมเดลใด

ขั้นตอนย่อยที่บันทึกใน Trace มักเรียกว่า **Span** แต่ละ Span สามารถมีเวลา สถานะ และ Attributes ของตนเองได้

### 8:33–9:17 — ตรวจรายละเอียดเพื่อหาคอขวด

ผู้บรรยายคลิกเหตุการณ์แต่ละรายการเพื่อดูข้อมูล เช่น:

- ระยะเวลาประมวลผล
- ชื่อ Operation
- Tool Call ID
- คำอธิบายเครื่องมือ
- Attributes ที่เกี่ยวข้อง

มีตัวเลือกกรองแสดงเฉพาะ **GenAI Attributes** เพื่อช่วยดูข้อมูลด้านการเรียกโมเดลและ Agent ได้สะดวกขึ้น

ในตัวอย่าง เหตุการณ์เรียกเครื่องมือแสดงว่าใช้เวลาประมาณ:

> **9.9 วินาที หรือ 4.7% ของเวลารวมตามที่หน้าจอคำนวณ**

ข้อมูลนี้ช่วยให้ตั้งคำถามได้ว่า:

- เวลาส่วนใหญ่หมดกับการสร้างเนื้อหาหรือไม่
- การ Deploy เป็นคอขวดจริงหรือไม่
- มีการเรียกโมเดลหลายรอบเกินจำเป็นหรือไม่
- มีขั้นตอนใดผิดจากที่ออกแบบไว้หรือไม่

แต่ต้องระวังการอ่านเวลา เพราะ Span อาจซ้อนกันหรือทำงานขนานกันได้ **จึงไม่ควรนำระยะเวลาทุก Span มาบวกตรง ๆ แล้วถือเป็นเวลารวม**

การเห็น Workflow ชื่อเดียวกันมากกว่าหนึ่งรายการก็ยังไม่ยืนยันว่ามีงานซ้ำ ต้องดูโครงสร้าง Parent–Child และรายละเอียดก่อน

Trace ช่วยตรวจเส้นทางการทำงานได้ แต่การตัดสินว่าเนื้อหาหรือผลลัพธ์ “ถูกต้อง” ยังต้องใช้เกณฑ์ประเมินเพิ่มเติม

### 9:18–9:39 — จบบท

ผู้บรรยายสรุปว่า Traces ช่วยให้เห็นเหตุการณ์ที่เกิดขึ้นระหว่าง Agent ประมวลผลคำขอ และเป็นส่วนสำคัญของ Observability

ข้อมูลเหล่านี้เป็นพื้นฐานสำหรับการปรับปรุง Agent เพราะทำให้เริ่มระบุได้ว่าปัญหาเกิดที่ขั้นตอนไหน แทนการดูเพียงคำตอบสุดท้าย

## สรุปท้ายเรื่อง

บทนี้เปิดความสามารถให้ **มองเห็นการทำงานของ Agent ที่ Deploy แล้ว** โดยทำสามส่วนหลัก:

**ตั้งค่า Telemetry → เพิ่มสิทธิ์เขียน Logs และ Traces → Deploy แล้วส่งคำขอทดสอบ**

จากนั้นใช้หน้าต่างต่าง ๆ ให้เหมาะกับคำถาม:

| ต้องการรู้อะไร | ดูจาก |
| --- | --- |
| มีการใช้งานมากน้อยแค่ไหน | Metrics และ Dashboard |
| ระบบบันทึกเหตุการณ์หรือข้อผิดพลาดอะไร | Logs |
| คำขอนี้ผ่านขั้นตอนใดและช้าตรงไหน | Traces |
| ผลลัพธ์ตอบโจทย์และถูกต้องหรือไม่ | การประเมินผลเพิ่มเติม |

สิ่งที่ควรจำมากที่สุด:

1. **Trace แสดงขั้นตอนที่บันทึกได้ ไม่ใช่ความคิดภายในทั้งหมดของโมเดล**
2. **การตั้งค่าและสิทธิ์ต้องครบทั้งคู่** จึงจะส่งข้อมูลติดตามได้
3. **หนึ่งข้อความจากผู้ใช้อาจมีหลายการเรียกภายใน** ต้องอ่าน Metric ตามนิยามของระบบ
4. **เปิด Trace ยังไม่เท่ากับปรับปรุงสำเร็จ** ต้องใช้ข้อมูลหาคอขวด แก้ไข แล้ววัดผลอีกครั้ง

เมื่อเชื่อมทั้งคอร์ส ตอนนี้ระบบตัวอย่างมีครบตั้งแต่ **สร้าง Agent → Deploy → กำหนดสิทธิ์และตรวจข้อความ → ติดตามการทำงาน** ส่วนบทนี้ยังไม่ได้สาธิตการประเมินคุณภาพคำตอบแบบ Evaluation Set หรือ LLM as a Judge
