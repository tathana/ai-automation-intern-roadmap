13 — Start Here: ได้รับงานแล้วเริ่มตรงไหน

หน้านี้เป็นประตูหลักสำหรับคนที่ได้รับโจทย์มาแล้ว แต่ยังไม่แน่ใจว่าต้องเปิดไฟล์ใดหรือเริ่มเขียนโค้ดตรงไหน

หลักสำคัญ: อย่าเริ่มจากการเลือกเทคโนโลยี ให้เริ่มจากทำความเข้าใจว่าใครกำลังเสียเวลากับอะไร และผลลัพธ์แบบใดจึงเรียกว่าแก้ปัญหาได้

เส้นทางหนึ่งโปรเจกต์

รับโจทย์
  ↓
เขียนสิ่งที่เข้าใจด้วยภาษาของเรา
  ↓
ถามผู้ใช้และดูขั้นตอนเดิม
  ↓
กำหนดสิ่งที่จะทำ / ไม่ทำ / วิธีตรวจว่าผ่าน
  ↓
วาดข้อมูลและเส้นทางงาน
  ↓
แบ่งเป็นชิ้นเล็กที่สาธิตได้
  ↓
เขียนโค้ด + test ทีละชิ้น
  ↓
รวมระบบ ทดลอง failure และตรวจโดยผู้ใช้
  ↓
release → observe → handoff

ไม่ต้องคิดทุกเรื่องให้สมบูรณ์ตั้งแต่วันแรก แต่ทุกครั้งก่อนขยับไปด่านถัดไป ต้องมีหลักฐานชิ้นเล็กว่าด่านปัจจุบันชัดพอแล้ว

ถ้าเพิ่งได้รับข้อความจากหัวหน้า

สมมติได้รับว่า “ช่วยใช้ AI ลดเวลาอ่าน Resume ให้ HR” ให้ทำเพียงสี่อย่างก่อน:

  1. จดโจทย์ต้นฉบับไว้โดยไม่ตีความเพิ่ม
  2. เขียนความเข้าใจของเรา 3–5 บรรทัด
  3. ทำรายการคำถามที่หากไม่รู้แล้วจะออกแบบผิด
  4. นัดคุยหรือส่งคำถามให้ผู้ใช้จริง

ยังไม่ควรสร้าง database schema, เลือกโมเดล หรือขอ AI เขียนระบบเต็ม เพราะสิ่งเหล่านั้นขึ้นกับคำตอบที่ยังไม่มี

แผนที่ว่าเมื่อใดควรเปิดหน้าไหน

สถานการณ์ ไปทำอะไร
เพิ่งรับงานและโจทย์ยังกว้าง Start Here และ Guided Workbook
ไม่รู้ว่าผู้ใช้ต้องการอะไร Requirement & Scope
รู้โจทย์แล้วแต่ไม่รู้ระบบหน้าตาอย่างไร Design & Work Breakdown
เปิด editor แล้วไม่รู้เริ่มไฟล์ไหน From Requirement to Code
อยากให้ AI ช่วยแต่กลัวได้โค้ดก้อนใหญ่ AI-assisted Coding
ไม่รู้ว่าต้อง test อะไร Testing & Failure Cases
กำลังจะ demo หรือ deploy Release & Handoff
อยากเห็นตัวอย่างที่กรอกและทำครบ Worked Example

กติกา Stop–Go

ก่อนเริ่มโค้ด ตอบคำถามต่อไปนี้ให้ได้อย่างน้อยหนึ่งประโยค:

  • ใครใช้ผลลัพธ์นี้
  • Input มาจากไหน
  • Output ต้องหน้าตาอย่างไร
  • อะไรห้ามระบบทำ
  • ตัวอย่างหนึ่งเคสที่ควรผ่าน
  • ตัวอย่างหนึ่งเคสที่ต้องปฏิเสธหรือส่งให้คนตรวจ
  • จะพิสูจน์อย่างไรว่าลดเวลาหรือแก้ปัญหาได้

หากยังตอบไม่ได้ ให้หยุดที่ discovery ไม่ใช่แก้ด้วยการเขียนโค้ดเดา

Definition of Ready แบบง่าย

งานหนึ่งชิ้นพร้อมให้เริ่มเขียนเมื่อ:

  • มีตัวอย่าง input ที่ใช้ทดสอบได้
  • บอก expected output ได้
  • รู้ว่าเมื่อข้อมูลผิดควรเกิดอะไร
  • ขอบเขตเล็กพอทำและตรวจได้ภายในหนึ่งช่วงงาน
  • รู้ว่าใครตอบคำถามเมื่อติดเรื่อง business rule

Definition of Ready คือเงื่อนไขก่อนเริ่มงาน ส่วน Definition of Done คือเงื่อนไขก่อนประกาศว่างานเสร็จ สองคำนี้ช่วยลดการเริ่มงานทั้งที่ยังขาดข้อมูล และลดการส่งงานที่ “รันได้แต่ยังตรวจไม่ได้”

เมื่อจบหน้านี้

คุณยังไม่จำเป็นต้องมีโค้ด แต่ต้องรู้ว่าตัวเองอยู่ด่านใด จากนั้นเปิด Guided Workbook และกรอกเฉพาะช่องของด่านนั้น

14 — Beginner Project Workbook: สมุดงานไฟล์เดียว

Workbook นี้ลดภาระการเลือก Template หลายไฟล์ ให้คัดลอกหัวข้อต่อไปนี้ไปไว้ใน docs/PROJECT_WORKBOOK.md แล้วเติมทีละส่วน ข้อใดยังไม่รู้ให้เขียน UNKNOWN — ถามใคร / เมื่อไร แทนการเดา

1. Project Snapshot

# Project: <ชื่อที่สื่อปัญหา>

## โจทย์ต้นฉบับ
<ข้อความจากผู้มอบหมาย>

## ความเข้าใจของเรา
ระบบนี้ช่วย <ผู้ใช้> ทำ <งาน> โดยลด <เวลา/ข้อผิดพลาด/ขั้นตอน>

## Success metric
- ก่อนทำ: ...
- เป้าหมายทดลอง: ...
- วิธีวัด: ...

## Owner และผู้ตัดสิน
- ผู้ใช้จริง:
- ผู้ให้ requirement:
- ผู้อนุมัติผลลัพธ์:

ถ้ายังไม่มี baseline ให้จดวิธีเก็บ ไม่ต้องสร้างตัวเลขขึ้นเอง เช่น “จับเวลาการอ่าน Resume 30 ไฟล์จากตัวอย่างสังเคราะห์หรือข้อมูลที่ได้รับอนุญาต”

2. Current Flow

ใครส่งอะไร
  ↓
ใครเปิด/อ่าน/คัดลอก
  ↓
ใช้กฎอะไรตัดสิน
  ↓
บันทึกผลไว้ที่ไหน
  ↓
ใครรับงานต่อ

ใต้ Flow ให้จดจุดช้า จุดผิดบ่อย และจุดที่ต้องใช้วิจารณญาณมนุษย์ อย่ารีบทำ automation ในขั้นที่ยังไม่เข้าใจกฎ

3. Scope Box

## In scope รอบนี้
- รับไฟล์ข้อความ/PDF ที่ระบบรองรับ
- สกัดข้อมูลตาม schema
- แสดงหลักฐานและส่งให้คนตรวจ

## Out of scope รอบนี้
- ตัดสินรับหรือปฏิเสธผู้สมัครอัตโนมัติ
- OCR เอกสารทุกชนิด
- เชื่อม production HR system ก่อนผ่าน pilot

## ข้อห้าม
- ห้าม log เนื้อหา Resume เต็ม
- ห้ามให้ model ทำ side effect โดยไม่มี approval

Out of scope ไม่ได้แปลว่าเรื่องนั้นไม่สำคัญ แต่แปลว่า “ยังไม่รับปากในรอบนี้”

4. Acceptance Examples

เขียนตัวอย่างก่อนเขียนโค้ด:

ID Given When Then
AC-01 Resume มี skill Python จริง วิเคราะห์ คืน skill พร้อม quote ที่ค้นพบในต้นฉบับ
AC-02 Provider คืน quote ที่ไม่มีจริง ตรวจ evidence ระบุ needs_review และไม่ยืนยันข้อมูลนั้น
AC-03 ส่ง event เดิมซ้ำ รับข้อมูล คืน task เดิมและไม่สร้างงานซ้ำ

Given–When–Then แปลแบบง่ายว่า “กำหนดสถานการณ์ → ทำบางอย่าง → คาดหวังผล” และสามารถเปลี่ยนเป็น test ภายหลังได้ตรง ๆ

6. Simple System Map

[Input] → [Validate] → [Save Task] → [Process] → [Review] → [Output]
               │             │            │
               └─ error      └─ retry     └─ audit

ทุกกล่องควรบอกได้ว่า “รับอะไร คืนอะไร เก็บ state หรือไม่ และล้มเหลวอย่างไร” หากกล่องหนึ่งทำหลายหน้าที่จนตอบยาก ให้แยกกล่อง

7. Work Slices

Slice Demo ที่เห็นได้ Code Test Done เมื่อ
S1 input ถูกต้องสร้าง task ได้ model + validation + repository valid/invalid input query task กลับมาได้
S2 worker สร้าง evidence provider + service supported/unsupported quote result ถูกบันทึก
S3 คนกด approve/reject review API + audit valid/duplicate decision audit ค้นย้อนหลังได้

หนึ่ง Slice ควรวิ่งจาก input ไปถึงผลที่มองเห็น ไม่ใช่ “ทำ database ทั้งหมด” โดยยังสาธิตอะไรไม่ได้

- สิ่งที่ทดลอง:
- หลักฐานหลังแก้:
- คำถาม/ความเสี่ยงที่ยังเหลือ:
- commit:

9. Release and Handoff

- [ ] รันจาก clean setup ตาม README ได้
- [ ] ไม่มี secret หรือข้อมูลจริงใน Git/log/test fixture
- [ ] happy path และ failure สำคัญผ่าน
- [ ] มีวิธีตรวจ health และงานค้าง
- [ ] มี rollback/disable switch
- [ ] ระบุ limitation ตรงไปตรงมา
- [ ] คนอื่นทดลองตาม runbook ได้

Workbook นี้เป็นเส้นหลัก ส่วน Template Pack ใช้เมื่อเรื่องใดซับซ้อนพอที่จะต้องแยกเอกสาร เช่น ADR หลายรายการ, risk register ใหญ่ หรือ release ที่มี migration
